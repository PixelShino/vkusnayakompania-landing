# Directus: установка и эксплуатация

Админка сайта. Клиент правит контент здесь, сайт собирается статикой и
обновляется сам через 10–20 секунд после «Сохранить» (с новыми фото — до минуты).

## Как устроено

| Что | Где |
|---|---|
| Сайт | `https://vkus-com.ru` → nginx → `/srv/vkus/current` (симлинк на релиз) |
| Админка | `https://admin.vkus-com.ru` → nginx → Directus в Docker на `127.0.0.1:8055` |
| Вебхук пересборки | `https://admin.vkus-com.ru/hooks/rebuild` → nginx → `webhook` на `127.0.0.1:9000` → `deploy/build.sh` |
| Код | `/srv/vkus/site` — клон этого репозитория, ветка `main` |
| Релизы | `/srv/vkus/releases/<дата-время>`, хранятся пять последних |
| Бэкапы | `/srv/backups`, 14 дней |
| Превью | Vercel, собирает ветку из того же Directus по токену сборщика |

Цепочка публикации: редактор нажимает «Сохранить» → Flow «Пересборка сайта»
шлёт `POST /hooks/rebuild` → `build.sh` забирает контент по REST, собирает
Astro в новый релиз и переключает симлинк. Упавшая сборка симлинк не трогает.
Ночью в 00:10 крон собирает сайт ещё раз, чтобы сработали окна показа афиши
и акций.

Ход сборки виден в самой админке, раздел «Публикация сайта». Первой стоит
панель «Ход сборки»: цветная полоса с процентами и шагом («проверяю»,
«получаю контент», «собираю страницы: фото 120 из 559», «публикую»).
Расширение `directus/extensions/build-status` перечитывает её раз в 2
секунды, пока идёт сборка. Когда сборка закончилась, страница один раз
перезагружается сама и показывает «Опубликовано» со временем и длительностью
или «Сборка не удалась» с последними строками лога. Туда пишет `build.sh`
токеном сборщика (`progress` и `step` берутся из вывода `pnpm build`). При
сборке без Directus (на фикстуре) отчёт пропускается, а сбой отчёта сборку
не роняет. Поле «Что на сайте» отвечает на главный вопрос редактора: «На
сайте всё, что сохранено до 16:51». Если своё «Сохранить» было позже этого
времени, правка ещё едет. Там же указано, что сохранено, но на сайт не
попало («Не опубликовано, черновики: 1 блюдо («Корпусная малина»)», «Вне дат
показа: 1 акция»), и что осталось заменить («Осталось заменить заглушки:
торты — 1, меню — 2», `scripts/site-report.mjs`).

После каждой сборки колокольчик в админке сообщает тем, чьи сохранения вошли в
релиз: «Ваши правки опубликованы: 2 блюда, 1 точка». Если запись осталась
черновиком, это сказано там же, со ссылкой на неё. Упавшая сборка приходит
администраторам как «Сборка сайта не удалась», не чаще раза в полчаса
(`scripts/build-notify.mjs`). Окно «чьи правки вошли» отсчитывается от начала
прошлой опубликованной сборки, отметка хранится в `/srv/vkus/published-since`.

Сторож `deploy/watch.sh` (крон раз в 2 минуты) сверяет журнал действий с
началом последней сборки: правка старше минуты, после которой сборка не
запустилась, — статус «Есть правки, которых нет на сайте» и пересборка.
Flow подписан и на `items.sort`: перетаскивание порядка тортов и акций
собирает сайт сразу, а не ночью.

Загрузки ужимаются на входе: расширение `directus/extensions/optimize-upload`
после каждой загрузки картинки переписывает файл под тем же id — не больше
2560 px по длинной стороне, JPEG (из JPEG/TIFF/AVIF) или WebP (из PNG,
прозрачность сохраняется), качество 85. PNG-скриншот на 2 МБ становится
120 КБ, печатное меню на 7 МБ — 400 КБ; заголовок, alt и связи не меняются.
GIF, SVG и HEIC не трогаются. PDF сжимает сборка: `fetch-files` прогоняет
документы тяжелее 1,5 МБ через Ghostscript (картинки 200 dpi, JPEG 85) —
печатное меню на 22 МБ уходит на сайт весом 1 МБ.

Секция «Фотогалерея» собирает кадры из двух мест. Сначала идут фото точек
(«Точки → Галерея зала», связка `places_files`), за ними — фото направлений
(«Направления → Фотогалерея», связка `directions_files`): боксы кейтеринга,
накрытые банкетные столы. Направления идут в порядке админки, кадры внутри —
в порядке перетаскивания. Под кадром подпись «Кейтеринг · Бокс с закусками»:
название направления и поле «Подпись» у фото; без подписи — одно название.
Файл с пометкой `[заглушка]` в заголовке встаёт штрихованной плашкой и
попадает в счётчик «фото направлений» в «Что на сайте».

## Установка на VPS

Ubuntu 22.04+, доступ root, DNS `vkus-com.ru`, `www.vkus-com.ru` и
`admin.vkus-com.ru` уже смотрят на сервер.

### 1. Сервер

```bash
apt update && apt install -y git nginx certbot python3-certbot-nginx webhook
curl -fsSL https://get.docker.com | sh
curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt install -y nodejs
npm install -g pnpm@10
adduser --disabled-password --gecos '' deploy
usermod -aG docker deploy
mkdir -p /srv/vkus /srv/backups && chown -R deploy:deploy /srv/vkus /srv/backups
```

Защита и память. Часовой пояс — Самара: ночная пересборка в 00:10 должна
совпадать с полуночью точек. Своп обязателен: на 2 ГБ сборка Astro доходит
до 1,5 ГБ, рядом работают Directus и Postgres.

```bash
timedatectl set-timezone Europe/Samara
apt install -y fail2ban ufw unattended-upgrades
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
printf 'vm.swappiness = 10\nnet.core.default_qdisc = fq\nnet.ipv4.tcp_congestion_control = bbr\n' >/etc/sysctl.d/90-vkus.conf
sysctl --system
ufw default deny incoming && ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw enable
printf 'PermitRootLogin prohibit-password\nPasswordAuthentication no\nKbdInteractiveAuthentication no\n' \
  >/etc/ssh/sshd_config.d/00-hardening.conf   # сначала положить свой ключ в authorized_keys
sshd -t && systemctl reload ssh
printf '[DEFAULT]\nbackend = systemd\nbanaction = ufw\n\n[sshd]\nenabled = true\nmode = normal\n' >/etc/fail2ban/jail.local
systemctl restart fail2ban
printf '{ "log-driver": "local", "log-opts": { "max-size": "10m", "max-file": "3" } }\n' >/etc/docker/daemon.json
systemctl restart docker
```

Для SSH `ufw allow`, а не `ufw limit`, и `fail2ban` в режиме `normal`, а не
`aggressive`: `ssh-keyscan` в GitHub Actions открывает пять соединений подряд,
и строгие правила банят раннер выкладки.

### 2. Код

```bash
su - deploy
git clone https://github.com/PixelShino/vkusnayakompania-landing.git /srv/vkus/site
cd /srv/vkus/site && pnpm install --frozen-lockfile
```

### 3. Directus

```bash
cd /srv/vkus/site/directus
cp .env.example .env
```

В `.env`: `SECRET` (`openssl rand -hex 32`), `PUBLIC_URL=https://admin.vkus-com.ru`,
`DB_PASSWORD`, `ADMIN_EMAIL` (настоящий адрес с обычным доменом: `.local` и
подобные Directus не принимает при входе), `ADMIN_PASSWORD`, блок SMTP
(`EMAIL_TRANSPORT=smtp` и данные почтового сервиса — без него не уйдут
приглашения и сброс пароля). `DIRECTUS_PORT` оставьте 8055.

```bash
docker compose up -d
curl -s http://127.0.0.1:8055/server/ping        # pong
docker compose cp snapshot.yaml directus:/directus/snapshot.yaml
docker compose exec -T directus node /directus/cli.js schema apply --yes /directus/snapshot.yaml
# … INFO: Snapshot applied successfully
```

Расширения из `directus/extensions/` контейнер читает с диска; после `git pull`
с новым или изменённым расширением — `docker compose restart directus`
(в логе `Loaded extensions: directus-extension-build-status, directus-extension-notify, directus-extension-optimize-upload, directus-extension-order-guard, directus-extension-request-guard`).

Снапшот схемы лежит в репо (`directus/snapshot.yaml`), контейнер его не видит,
поэтому файл сначала копируется внутрь. CLI зовётся через `node /directus/cli.js`:
`npx directus` в образе не находит бинарник и качает пакет из npm заново.

Дальше роли, сборщик и Flow одним скриптом. Нужен статический токен
администратора: в админке «Пользователи → админ → Token → Generate», сохранить.

```bash
cd /srv/vkus/site
DIRECTUS_URL=http://127.0.0.1:8055 DIRECTUS_ADMIN_TOKEN=<токен админа> \
REBUILD_HOOK_URL=https://admin.vkus-com.ru/hooks/rebuild REBUILD_HOOK_SECRET=<секрет вебхука> \
pnpm setup
```

Скрипт напечатает `DIRECTUS_TOKEN` сборщика — он нужен в следующем шаге и
больше не показывается. Секрет вебхука придумайте сами (`openssl rand -hex 24`).
Адрес вебхука — публичный: Flow выполняется внутри контейнера Directus, и
`127.0.0.1:9000` там указывает на сам контейнер, а не на сервер.

Имя проекта, цвет и русский язык админки (в том числе на странице входа) ставит
тот же скрипт. Дальше в админке создайте пользователей редакторов с ролью
«Редактор» («Пользователи → +», роль «Редактор», приглашение уйдёт письмом).

### 4. Сайт

```bash
cd /srv/vkus/site
cp .env.example .env
```

В `.env`: `DIRECTUS_URL=http://127.0.0.1:8055`, `DIRECTUS_TOKEN=<токен сборщика>`,
`PUBLIC_YANDEX_MAPS_KEY=<ключ JS API Яндекс Карт>`, `SITE=https://vkus-com.ru`,
`PUBLIC_DIRECTUS_URL=https://admin.vkus-com.ru` (куда корзина отправляет заказ,
см. «Каталог доставки и заказы»).

Первый контент: сайт не соберётся без телефона, двух точек, пяти направлений,
фото первого экрана и SEO-полей (см. `pnpm test`). У точки есть своё поле
«Телефон точки»: пустое — на странице стоит общий номер из «Настроек». Заполните «Настройки»,
«Главная», «Точки» и «Направления» в админке — либо загрузите стартовый набор
из фикстуры: `pnpm exec node scripts/import-fixture.mjs` (заводит записи и
файлы из `src/data/fixture.json`, существующее не трогает; фото там
заглушки, их заменяют редакторы).

```bash
deploy/build.sh        # первый релиз, /srv/vkus/current появился
```

### 5. nginx и сертификаты

Конфиги из репо ссылаются на сертификаты, которых ещё нет, и с ними `nginx -t`
не проходит. Поэтому сначала временный блок на `:80` для выпуска, потом конфиги:

```bash
cat >/etc/nginx/sites-enabled/acme <<'EOF'
server { listen 80; server_name vkus-com.ru www.vkus-com.ru admin.vkus-com.ru; return 404; }
EOF
nginx -t && systemctl reload nginx
certbot certonly --nginx -d vkus-com.ru -d www.vkus-com.ru
certbot certonly --nginx -d admin.vkus-com.ru
rm /etc/nginx/sites-enabled/acme /etc/nginx/sites-enabled/default
cp deploy/nginx/10-vkus-tuning.conf /etc/nginx/conf.d/
cp deploy/nginx/vkus-com.ru.conf /etc/nginx/sites-available/vkus-com.ru
cp deploy/nginx/admin.vkus-com.ru.conf /etc/nginx/sites-available/admin.vkus-com.ru
ln -s /etc/nginx/sites-available/vkus-com.ru /etc/nginx/sites-enabled/
ln -s /etc/nginx/sites-available/admin.vkus-com.ru /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
```

Certbot сам добавит таймер продления.

Кеш дескрипторов (`open_file_cache`) выключен намеренно: релиз переключается
симлинком `current`, а с кешем nginx до двух минут отдавал `index.html`
прошлого релиза и помнил `404` на файлы, которые уже появились. Страница и
`/media/` отдаются с `Cache-Control: no-cache`: браузер перепроверяет их при
каждом заходе (неизменённые — одним `304`), поэтому правка видна сразу, а
адреса документов не меняются при замене файла.

Прокси для сборки. Directus не отвечает `304` на повторный запрос картинки, и
Astro при каждой сборке заново пережимает все фото: минута вместо нескольких
секунд. Локальный nginx на `127.0.0.1:8056` сверяет `If-Modified-Since` и
отдаёт `304`, если файл не менялся; сборка ходит в Directus через него:

```bash
mkdir -p /var/cache/nginx/directus-assets && chown www-data: /var/cache/nginx/directus-assets
cp deploy/nginx/directus-build.conf /etc/nginx/sites-available/directus-build
ln -s /etc/nginx/sites-available/directus-build /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
sed -i 's|^DIRECTUS_URL=.*|DIRECTUS_URL=http://127.0.0.1:8056|' /srv/vkus/site/.env
```

### 6. Приёмник вебхука

`hooks.json` берёт секрет из окружения, поэтому `webhook` запускается с
флагом `-template`. Юнит из пакета Ubuntu стартует только при наличии
`/etc/webhook.conf` — условие снимается пустым `ConditionPathExists=`.
`-verbose` пишет вывод сборки в журнал: `journalctl -u webhook`.

```bash
cat >/etc/default/webhook <<'EOF'
HOOK_SECRET=<секрет вебхука, тот же что в pnpm setup>
EOF
chmod 600 /etc/default/webhook
mkdir -p /etc/systemd/system/webhook.service.d
cat >/etc/systemd/system/webhook.service.d/override.conf <<'EOF'
[Unit]
ConditionPathExists=

[Service]
User=deploy
EnvironmentFile=/etc/default/webhook
ExecStart=
ExecStart=/usr/bin/webhook -verbose -nopanic -template -ip 127.0.0.1 -port 9000 -hooks /srv/vkus/site/deploy/webhook/hooks.json
EOF
systemctl daemon-reload && systemctl enable --now webhook
curl -s -X POST -H 'X-Hook-Secret: <секрет>' http://127.0.0.1:9000/hooks/rebuild   # принято, сборка запущена
```

### 8. Выкладка кода из GitHub

В репозитории: `Settings → Secrets and variables → Actions`: переменная
`VPS_HOST` (IP или домен) и секрет `VPS_SSH_KEY` (приватный ключ, публичный —
в `/home/deploy/.ssh/authorized_keys`). После этого пуш в `main` собирает сайт
на сервере. Пока переменной нет, workflow пропускается.

Ключ стоит ограничить одной командой выкладки: даже утёкший, он не даст
шелла на сервере.

```
command="cd /srv/vkus/site && git pull --ff-only && deploy/build.sh",restrict ssh-ed25519 AAAA… github-actions
```

### 9. Проверка

1. В админке измените заголовок афиши и сохраните.
2. В «Публикации сайта» пойдёт полоса «Идёт сборка». Когда она дойдёт до
   конца, страница сама сменится на «Опубликовано», в колокольчике появится
   «Ваши правки опубликованы: 1 событие афиши», а `https://vkus-com.ru`
   покажет новый заголовок.
3. `ls -la /srv/vkus/current` указывает на свежий релиз; вывод сборки —
   `journalctl -u webhook`.

## Эксплуатация

- **Статус сборки**: в админке «Публикация сайта»; при ошибке там же хвост лога.
  «Есть правки, которых нет на сайте» дольше пяти минут — смотреть
  `/srv/vkus/watch.log` и `journalctl -u webhook`.
- **Сжатие загрузок**: строки `optimize-upload:` в логе Directus; «не сжат» —
  файл оставлен как загружен, сайт всё равно пережмёт его на сборке.
- **Логи**: `docker compose -f /srv/vkus/site/directus/docker-compose.yml logs -f directus`;
  ночные сборки — `/srv/vkus/build.log`; сборки после сохранения — `journalctl -u webhook`.
- **Пересобрать руками**: `sudo -u deploy /srv/vkus/site/deploy/build.sh`.
- **Обновить Directus**: поменять тег образа в `directus/docker-compose.yml`,
  `docker compose pull && docker compose up -d`. Перед этим бэкап.
- **Бэкап**: `deploy/backup.sh` (крон делает ночью). Восстановление:
  `gunzip -c /srv/backups/db-<дата>.sql.gz | docker compose exec -T database psql -U directus directus`
  и распаковать `uploads-<дата>.tar.gz` в `directus/`.
- **Схема поменялась** (новое поле): изменить в локальном Directus, выгрузить
  `GET /schema/snapshot?export=yaml` в `directus/snapshot.yaml`, закоммитить,
  на сервере — строго в таком порядке:
  1. `schema apply` из шага 3;
  2. сбросить кеш схемы: `curl -X POST -H "Authorization: Bearer <admin>" \
     http://127.0.0.1:8055/utils/cache/clear?system` или
     `docker compose restart directus`. CLI работает отдельным процессом, а
     кеш схемы у запущенного Directus в памяти: до сброса новая коллекция для
     API «не существует» (`FORBIDDEN`);
  3. `node scripts/directus-setup.mjs` (`pnpm setup`) — права редактора и
     сборщика на новую коллекцию, её место в Flow; дописывает только недостающее;
  4. `sudo -u deploy deploy/build.sh` — иначе сайт соберётся только по
     следующей правке или по сторожу.
- **Токены**: сборщика — в `/srv/vkus/site/.env` и в переменных Vercel;
  секрет вебхука — в `/etc/default/webhook` и в Flow «Пересборка сайта».
  Отозвать токен сборщика: «Пользователи → Сборщик сайта → Token».
- **Оповещения о заказах** (почта, Telegram, журнал, `POST /notify/test`,
  включение SMTP): [NOTIFY.md](NOTIFY.md).

## Редактору: почему не вижу правку на сайте

Сначала откройте «Публикацию сайта». Если там идёт полоса, правка едет:
подождите, страница обновится сама. Если там «Опубликовано», прочитайте «Что
на сайте»: в нём перечислено всё, что сохранено, но не показывается.
Дальше по порядку:

1. **Черновик.** На сайт попадает только статус «Опубликовано». Если у
   записи «Черновик», вверху карточки висит жёлтая плашка «Черновик — блюдо не
   попадёт на сайт», а после сборки об этом скажет и колокольчик. Новое блюдо
   в «Блюдах» по умолчанию сразу «Опубликовано». В тортах, акциях, афише и
   меню новая запись по-прежнему создаётся черновиком (акцию и событие удобно
   готовить заранее), поэтому перед сохранением смотрите на статус.
2. **«Есть в наличии».** Блюдо без этой галочки остаётся на сайте серым в
   конце раздела, и заказать его нельзя. Скрытый раздел (черновик или архив)
   прячет и все свои блюда. Блюдо без цены на сайт не попадает.
3. **Даты показа.** Акция и событие афиши видны только между «Показывать с»
   и «Показывать по», включительно. В «Что на сайте» такие записи
   перечислены как «Вне дат показа». Ночная сборка в 00:10 включает и
   выключает их сама. Акция, где упомянуто приложение, на сайт не выходит
   (см. «Акции»).
4. **Идёт сборка.** Сборка занимает 10–30 секунд, с новыми фото до минуты.
   Правка, сохранённая во время сборки, уходит следующей сборкой сразу
   следом. «Ошибка сборки» значит, что на сайте осталась прежняя версия:
   перешлите разработчику текст из «Что пошло не так».
5. **Кеш браузера.** Если на сайте всё ещё старое, обновите страницу: на
   компьютере Ctrl+F5 (Cmd+Shift+R на Mac), на телефоне потяните страницу
   вниз. Можно открыть сайт в режиме инкогнито. Фото и меню отдаются без
   долгого кеша, но браузер мог открыть вкладку из памяти.

## Оповещения и ход сборки: выкатка на прод

1. `git pull`, затем `docker compose restart directus`. В логе должно быть
   `Loaded extensions: directus-extension-build-status, directus-extension-notify, …`.
2. `schema apply` по `directus/snapshot.yaml`, затем сброс кеша схемы. Схема
   добавляет «Оповещения», «Журнал оповещений», поле «Оповещения» у заказов и
   заявок, `progress`/`step` у «Публикации сайта», плашки «Черновик» у восьми
   коллекций и `published` по умолчанию у `products.status`. Сборка между
   `git pull` и `schema apply` пройдёт, но не запишет свой статус
   (`статус сборки не записан: 400`): нового поля ещё нет.
3. `pnpm setup`. Редактору даются «Оповещения» без токена бота и журнал на
   чтение, сборщику — уведомления и роли пользователей для колокольчика.
4. `sudo -u deploy deploy/build.sh`. Первая сборка создаёт отметку
   `/srv/vkus/published-since`, уведомления «Ваши правки опубликованы»
   начинаются со следующей.
5. «Оповещения»: адреса, бот, чаты, затем `POST /notify/test` (см. [NOTIFY.md](NOTIFY.md)).

## Каталог доставки и заказы

Страница `/catalog/` — каталог доставки на сайте, перенесённый импортом из
магазина FoodPicasso (`vkusdostavka.shop`): 13 разделов, около 120 блюд. С
12.10.2026 каталог на сайте и есть магазин: страницы не ссылаются ни на
приложение, ни на `vkusdostavka.shop`. Гость собирает
корзину, оставляет имя и телефон — заказ падает в админку, менеджер перезванивает
и подтверждает состав, сумму, адрес и время. Оплаты на сайте нет: оплату и
стоимость доставки обсуждают при звонке.

**Коллекции** (группа «Каталог доставки»):

| Коллекция | Что | Кто правит |
|---|---|---|
| `product_categories` «Разделы» | название, адрес раздела (`slug`), порядок, статус | редактор |
| `products` «Блюда» | раздел, название, цена и старая цена, вес, размеры (`variants`: название, вес, цена), начинки на выбор (`fillings`), фото с alt, описание, состав, «В наличии», «Хит» / «Новинка», статус, порядок | редактор |
| `orders` «Заказы» | номер, статус (новый → в работе → выполнен / отменён), имя, телефон, доставка с адресом или самовывоз с точкой, время, комментарий, строки и сумма, источник, заметка менеджера | редактор (без удаления); сайт — только создание |

- **Нет в наличии** — снять галочку «В наличии»: блюдо остаётся на сайте серым
  в конце раздела, в корзину не кладётся, а у тех, у кого оно уже в корзине,
  заказ не уйдёт, пока его не уберут. **Скрыть совсем** — статус «Черновик»
  или «Архив». Скрытый раздел прячет и все свои блюда.
- **Размеры** — список «Размеры» в блюде: у каждого своя цена. Один размер
  сайт сворачивает в цену блюда. **Начинки** — теги «Начинки на выбор»: гость
  обязан выбрать одну, иначе торт не добавить; цена от начинки не зависит.
- Пустые разделы и блюда без цены на сайт не попадают (сборка пишет
  предупреждение). Без фото блюдо встаёт с плашкой «Фото скоро».
- Каталог необязателен: если коллекций нет или они пусты, сайт собирается
  как раньше, страница каталога показывает «Каталог обновляется» и закрыта от
  индексации, а ссылки «Доставка» ведут в магазин.

**Заказы в админке.** Список «Заказы» открывается новыми сверху, закладки
«Новые» и «В работе». В карточке заказа, пока статус «Новый», вверху
подсказка: «Оплаты на сайте нет: гость ждёт звонка. Позвоните, подтвердите
состав, сумму, адрес и время — и переведите заказ в „В работе“». Каждый новый заказ с сайта приходит уведомлением
(колокольчик в админке) всем активным пользователям с ролями «Administrator» и
«Редактор»; письмом — только когда настроен SMTP. Заказ, принятый по телефону,
редактор заводит сам («Источник: телефон»).

**Защита заказа.** Публичная роль может только *создать* заказ и не может
прочитать ни один, в том числе свой. Расширение
`directus/extensions/order-guard` проверяет заказ до записи: имя, российский
телефон, согласие, адрес или точку; строки собирает заново из `products` по
текущим ценам (браузер называет только блюдо, размер, начинку и количество),
сумму считает само, статус «Новый» и источник «Сайт» ставит само. Если цена
в админке поменялась после сборки сайта, в «Заметке менеджера» будет «На сайте
гость видел …, по текущим ценам …». Не больше 6 заказов за 10 минут с одного
адреса; адрес берётся из `X-Forwarded-For` nginx при `IP_TRUST_PROXY=1`
(в `docker-compose.yml`), подставить чужой адрес в начало заголовка нельзя.
Правила хука и формы на сайте одни и те же (`src/lib/order.ts`), паритет
телефона и веса проверяет `pnpm test`.

**Откуда браузер шлёт заказ.** Корзина отправляет `POST <PUBLIC_DIRECTUS_URL>/items/orders`
прямо из браузера, поэтому Directus должен разрешить сайту CORS:

```env
# directus/.env
CORS_ORIGIN=https://vkus-com.ru,https://www.vkus-com.ru   # это и есть значение по умолчанию
```

```env
# .env сайта (и переменные Vercel, если превью должно принимать заказы)
PUBLIC_DIRECTUS_URL=https://admin.vkus-com.ru
```

Без `PUBLIC_DIRECTUS_URL` корзина работает, но вместо формы предлагает
оформить заказ в магазине или по телефону. Превью на Vercel с чужим доменом
заказы не отправит, пока его адрес не добавлен в `CORS_ORIGIN` — так и задумано.

**Импорт из магазина.** У FoodPicasso нет открытого API, поэтому
`scripts/import-catalog.mjs` читает HTML страниц разделов `vkusdostavka.shop`:
блюда — блоки `.ddish` с `data-id`, `data-prices` (рубли × 10 000: `6850000` —
это 685 ₽), `data-modifiers` (размеры и начинки), `data-media` (фото);
«стоп-лист» — класс `ddish--stop`. Фото берутся в исходном размере с CDN
магазина и грузятся через `/files/import` в папку «Каталог» (дальше их ужимает
`optimize-upload`). Связка записи с магазином — поле `source_id`.

```bash
DIRECTUS_URL=http://127.0.0.1:8055 DIRECTUS_ADMIN_TOKEN=<токен админа> \
  node scripts/import-catalog.mjs --dry-run     # что изменится, без записи
node scripts/import-catalog.mjs                 # первый импорт: заводит недостающее, существующее не трогает
node scripts/import-catalog.mjs --sync          # сверить с магазином: цены, веса, наличие, размеры; пропавшие блюда — в архив
```

Флаги: `--no-photos` (без фото), `--save file.json` (сохранить разбор),
`--from file.json` (импорт из сохранённого разбора, без сети), `SHOP_URL` —
другой адрес магазина. Повторный запуск без изменений в магазине ничего не
меняет. Обычный импорт не перезаписывает правки редактора (только дозагружает
фото блюдам без фото); `--sync` переписывает поля магазина (название,
описание, цену, вес, размеры, начинки, наличие, бейджи, раздел, порядок) и
только там, где они разошлись, а фото, alt, слаг и состав оставляет. Блюдо,
которое снова появилось в магазине, `--sync` возвращает из архива; черновики
не трогает. Скрыть блюдо навсегда, несмотря на магазин, — статус «Черновик».

**Выкатка каталога на прод** — строго по порядку:

1. `git pull` на сервере, `docker compose restart directus` — подхватить
   `order-guard` и новые `CORS_ORIGIN` / `IP_TRUST_PROXY` (для env нужен
   `docker compose up -d directus`, простой `restart` их не перечитывает);
2. `schema apply` из шага 3 (`directus/snapshot.yaml`);
3. сброс кеша схемы (`/utils/cache/clear?system` или `restart directus`);
4. `pnpm setup` — права редактора на разделы, блюда и заказы, публичное
   «только создание» заказа, закладки, Flow на `product_categories` и `products`;
5. импорт каталога: `node scripts/import-catalog.mjs` с `DIRECTUS_URL` и токеном
   админа сервера (через туннель или на самом сервере);
6. `PUBLIC_DIRECTUS_URL=https://admin.vkus-com.ru` в `/srv/vkus/site/.env`;
7. `sudo -u deploy deploy/build.sh` и проверка: `/catalog/`, тестовый заказ,
   уведомление в админке, удалить тестовый заказ.

**Заявки.** Форма внизу каждой страницы: имя, телефон (маска `+7`), дата,
гостей, формат (кнопки или «Ещё не решили»), где (зал на Садовой, зал на
Советской Армии, выезд с адресом, «пока не знаю»), пожелания, согласие.
Обязательны только имя, телефон и согласие. Черновик формы хранится в
браузере, «Обсудить формат» на развороте выбирает формат в форме. После
отправки — экран «Заявка принята» с номером и тем, что гость указал; при
ошибке сети, 400 или 429 — понятное сообщение и номер для звонка. Без
`PUBLIC_DIRECTUS_URL` форма заменяется звонком.

В админке «Заявки на кейтеринг» открываются новыми сверху, закладки «Новые»
и «В работе» (в работе + договор). Пока статус «Новая», в карточке подсказка
перезвонить. Каждая заявка с сайта приходит уведомлением (колокольчик) ролям
«Administrator» и «Редактор»: «Заявка на кейтеринг 1210-4821 · 40 гостей»,
в тексте имя, телефон, дата, гости, формат, зал или адрес, пожелания.

**Защита заявки** — расширение `directus/extensions/request-guard`, как у
заказов: публичная роль только *создаёт* заявку и не читает ни одной; хук до
записи проверяет имя, российский телефон, согласие, дату (не в прошлом и не
дальше двух лет), гостей (1-2000), зал (существующий) или адрес, формат
(опубликованный); номер `ДДММ-NNNN`, статус «Новая» и источник «Сайт» ставит
сам, заметку менеджера от гостя не принимает. Не больше 5 заявок за 10 минут
с одного адреса (тот же `X-Forwarded-For` + `IP_TRUST_PROXY=1`). Заявка,
заведённая редактором в админке, хуком не проверяется. Правила хука и сайта
(`src/lib/request.ts`) одни и те же — паритет проверяет `pnpm test`. CORS —
тот же `CORS_ORIGIN`, что у заказов.

**Импорт со старого сайта.** REST API WordPress отдаёт у страниц пустой
`content` (тема рисует их PHP-шаблонами), поэтому `scripts/import-catering.mjs`
читает HTML пяти страниц (`/`, `/services/`, `/about/`, `/contacts/`, `/faq/`):
первый экран, цифры, приоритеты, форматы, шаги и переписку, постскриптум,
бонус заявки, все вопросы по темам и фото. Тексты переносятся как есть, с
лёгкой правкой (опечатки, «₽ на гостя» вместо «руб./чел.», неразрывные
пробелы); цены и «что входит» форматов собраны из ответов FAQ старого сайта
(источник — в комментариях `FORMAT_FACTS`). Фото — через `/files/import` в
папку «Кейтеринг» с осмысленными заголовком и alt. Связка записи с импортом —
поле `import_key`, файла — пометка в описании.

```bash
DIRECTUS_URL=http://127.0.0.1:8055 DIRECTUS_ADMIN_TOKEN=<токен админа> \
  node scripts/import-catering.mjs --dry-run   # что будет записано, без записи
node scripts/import-catering.mjs               # первый импорт: заводит недостающее, пустые поля страницы заполняет
node scripts/import-catering.mjs --sync        # переписать поля из импорта у уже заведённого (правки редактора будут потеряны)
```

Флаги: `--no-photos`, `--save file.json` (сохранить разбор), `--from file.json`
(импорт из сохранённого разбора без чтения страниц; фото всё равно берутся
со старого сайта), `--plan file.json` (что будет записано — для проверки
глазами), `OLD_SITE` — другой адрес старого сайта. Повторный запуск ничего не
дублирует и без `--sync` ничего не перезаписывает. Импорт нужно прогнать
**до** выключения старого сайта; без него раздел можно поднять из фикстуры
(`scripts/import-fixture.mjs` заливает и кейтеринг, если он пуст).

**Выкатка кейтеринга на прод** — строго по порядку:

1. `git pull` на сервере, `docker compose restart directus` — подхватить
   `request-guard` (в логе `Loaded extensions: …, directus-extension-request-guard`);
2. `schema apply` из шага 3 (`directus/snapshot.yaml`);
3. сброс кеша схемы (`/utils/cache/clear?system` или `restart directus`);
4. `pnpm setup` — права редактора на страницу, форматы, шаги, вопросы и
   заявки, сборщику — чтение раздела (не заявок), публичное «только создание»
   заявки, список и закладки заявок, Flow на коллекции раздела;
5. `node scripts/import-catering.mjs --dry-run`, затем без флага — с
   `DIRECTUS_URL` и токеном админа сервера;
6. `sudo -u deploy deploy/build.sh` и проверка: `/catering/`,
   `/catering/services/`, `/catering/faq/`, тестовая заявка, уведомление в
   админке, удалить тестовую заявку;
7. владельцу — переадресация старого домена: `vkusnayakompania.ru/` →
   `https://vkus-com.ru/catering/`, `/services/` → `/catering/services/`,
   `/faq/` → `/catering/faq/`, `/about/` → `/catering/#about`,
   `/contacts/` → `/catering/#contacts` (301).

## Акции: как набирать, чтобы лист не развалился

Секция «Акции» — печатный лист: первая акция по порядку (`sort`) — оттиск с
крупной цифрой, остальные — нумерованный реестр. Форму держит страница, а не
редактор, но три правила набора делают её лучше:

- **Заголовок — до 45 знаков**, одна мысль: «Скидка 20 % на первый заказ».
  Число со знаком `%` в заголовке первой акции страница вынимает и печатает
  крупно (`20 %`), остаток заголовка идёт подписью под ним. Без процента на
  месте цифры встаёт сам заголовок.
- **Текст — одно условие, до 110 знаков.** На странице остаётся первое
  предложение, остальное режется; в реестре — не больше трёх строк.
- **Первая по `sort` — витрина.** Ставьте первой общую акцию с процентом:
  оттиск с цифрой на бумаге и есть то, за что цепляется глаз. Точка задаётся
  полем `place`; пустое поле печатается как «Обе точки».

Окна показа (`show_from` / `show_until`) работают как прежде: вне окна акция
не собирается, ночной крон пересобирает сайт в 00:10.

**Приложения на сайте нет** (решение владельца 12.10.2026). Акция, в
заголовке или тексте которой есть «приложение», App Store, Google Play или
`vkusdostavka.shop`, на сайт не попадает, а сборка пишет в журнал
«акция «…» действует в приложении — на сайте не показана». Если скидка
действует и для заказов с сайта — уберите упоминание приложения из текста, и
акция вернётся. Так же из текстов главной («Настройки» → тексты секций)
выпадает каждое предложение про приложение. Поля приложения и старого
магазина (`app_ios`, `app_android`, `shop_url`, `shop_*`, а также
`delivery_title`, `delivery_text`, `delivery_note`, `app_screenshot`) в
схеме остались, но страница их не выводит — заполнять не нужно.

Поля `yandex_score`, `yandex_ratings`, `yandex_reviews`, `yandex_highlights`
в «Настройках» страница больше не показывает: цифры спорили с живым виджетом
Яндекс Карт, а источник у отзывов один — виджет. Заполнять их не нужно;
`yandex_award` («Хорошее место 2026») по-прежнему печатается.

## Локальная разработка

```bash
cd directus && cp .env.example .env    # заполнить SECRET, DB_PASSWORD, ADMIN_*
docker compose up -d
cd .. && cp .env.example .env          # DIRECTUS_URL=http://localhost:8055
pnpm setup                             # нужен DIRECTUS_ADMIN_TOKEN, см. выше
node scripts/import-catalog.mjs        # каталог доставки из магазина (тот же токен)
pnpm fixture                           # выгрузить контент в фикстуру
pnpm dev                               # http://127.0.0.1:4321
```

Заказы из корзины локально: в `directus/.env` —
`CORS_ORIGIN=http://127.0.0.1:4321,http://localhost:4321`, в `.env` сайта —
`PUBLIC_DIRECTUS_URL=http://127.0.0.1:8055`, затем `docker compose up -d directus`.

Без `DIRECTUS_URL` в `.env` сайт собирается из `src/data/fixture.json`; файлы
фикстуры в `src/data/fixture-files/` лежат в git, поэтому сборка проходит на
чистом клоне и на CI без Directus. `pnpm fixture` их перезаписывает — после
правок контента в админке изменения в этой папке коммитятся вместе с
`fixture.json`. `public/media/` из них собирает `prebuild`, она в `.gitignore`.
