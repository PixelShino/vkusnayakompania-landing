# Directus: установка и эксплуатация

Админка сайта. Клиент правит контент здесь, сайт собирается статикой и
обновляется сам через 10–20 секунд после «Сохранить» (с новыми фото — до минуты).

## Как устроено

| Что | Где |
|---|---|
| Сайт | `https://vkus-com.ru` → nginx → `/srv/vkus/current` (симлинк на релиз) |
| Админка | `https://admin.vkus-com.ru` → nginx → Directus в Docker на `127.0.0.1:8055` |
| Вебхук пересборки | `https://admin.vkus-com.ru/hooks/rebuild` → nginx → `webhook` на `127.0.0.1:9000` → `deploy/build.sh` |
| Код | `/srv/vkus/site` — клон этого репозитория, ветка `main` |
| Релизы | `/srv/vkus/releases/<дата-время>`, хранятся пять последних |
| Бэкапы | `/srv/backups`, 14 дней |
| Превью | Vercel, собирает ветку из того же Directus по токену сборщика |

Цепочка публикации: редактор нажимает «Сохранить» → Flow «Пересборка сайта»
шлёт `POST /hooks/rebuild` → `build.sh` забирает контент по REST, собирает
Astro в новый релиз и переключает симлинк. Упавшая сборка симлинк не трогает.
Ночью в 00:10 крон собирает сайт ещё раз, чтобы сработали окна показа афиши
и акций.

Ход сборки виден в самой админке, раздел «Публикация сайта». Первой стоит
панель «Ход сборки»: цветная полоса с процентами и шагом («проверяю»,
«получаю контент», «собираю страницы: фото 120 из 559», «публикую»).
Расширение `directus/extensions/build-status` перечитывает её раз в 2
секунды, пока идёт сборка. Когда сборка закончилась, страница один раз
перезагружается сама и показывает «Опубликовано» со временем и длительностью
или «Сборка не удалась» с последними строками лога. Туда пишет `build.sh`
токеном сборщика (`progress` и `step` берутся из вывода `pnpm build`). При
сборке без Directus (на фикстуре) отчёт пропускается, а сбой отчёта сборку
не роняет. Поле «Что на сайте» отвечает на главный вопрос редактора: «На
сайте всё, что сохранено до 16:51». Если своё «Сохранить» было позже этого
времени, правка ещё едет. Там же указано, что сохранено, но на сайт не
попало («Не опубликовано, черновики: 1 блюдо («Корпусная малина»)», «Вне дат
показа: 1 акция»), и что осталось заменить («Осталось заменить заглушки:
торты — 1, меню — 2», `scripts/site-report.mjs`).

После каждой сборки колокольчик в админке сообщает тем, чьи сохранения вошли в
релиз: «Ваши правки опубликованы: 2 блюда, 1 точка». Если запись осталась
черновиком, это сказано там же, со ссылкой на неё. Упавшая сборка приходит
администраторам как «Сборка сайта не удалась», не чаще раза в полчаса
(`scripts/build-notify.mjs`). Окно «чьи правки вошли» отсчитывается от начала
прошлой опубликованной сборки, отметка хранится в `/srv/vkus/published-since`.

Сторож `deploy/watch.sh` (крон раз в 2 минуты) сверяет журнал действий с
началом последней сборки: правка старше минуты, после которой сборка не
запустилась, — статус «Есть правки, которых нет на сайте» и пересборка.
Flow подписан и на `items.sort`: перетаскивание порядка тортов и акций
собирает сайт сразу, а не ночью.

Загрузки ужимаются на входе: расширение `directus/extensions/optimize-upload`
после каждой загрузки картинки переписывает файл под тем же id — не больше
2560 px по длинной стороне, JPEG (из JPEG/TIFF/AVIF) или WebP (из PNG,
прозрачность сохраняется), качество 85. PNG-скриншот на 2 МБ становится
120 КБ, печатное меню на 7 МБ — 400 КБ; заголовок, alt и связи не меняются.
GIF, SVG и HEIC не трогаются. PDF сжимает сборка: `fetch-files` прогоняет
документы тяжелее 1,5 МБ через Ghostscript (картинки 200 dpi, JPEG 85) —
печатное меню на 22 МБ уходит на сайт весом 1 МБ.

Секция «Фотогалерея» собирает кадры из двух мест. Сначала идут фото точек
(«Точки → Галерея зала», связка `places_files`), за ними — фото направлений
(«Направления → Фотогалерея», связка `directions_files`): боксы кейтеринга,
накрытые банкетные столы. Направления идут в порядке админки, кадры внутри —
в порядке перетаскивания. Под кадром подпись «Кейтеринг · Бокс с закусками»:
название направления и поле «Подпись» у фото; без подписи — одно название.
Файл с пометкой `[заглушка]` в заголовке встаёт штрихованной плашкой и
попадает в счётчик «фото направлений» в «Что на сайте».

## Установка на VPS

Ubuntu 22.04+, доступ root, DNS `vkus-com.ru`, `www.vkus-com.ru` и
`admin.vkus-com.ru` уже смотрят на сервер.

### 1. Сервер

```bash
apt update && apt install -y git nginx certbot python3-certbot-nginx webhook
curl -fsSL https://get.docker.com | sh
curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt install -y nodejs
npm install -g pnpm@10
adduser --disabled-password --gecos '' deploy
usermod -aG docker deploy
mkdir -p /srv/vkus /srv/backups && chown -R deploy:deploy /srv/vkus /srv/backups
```

Защита и память. Часовой пояс — Самара: ночная пересборка в 00:10 должна
совпадать с полуночью точек. Своп обязателен: на 2 ГБ сборка Astro доходит
до 1,5 ГБ, рядом работают Directus и Postgres.

```bash
timedatectl set-timezone Europe/Samara
apt install -y fail2ban ufw unattended-upgrades
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab
printf 'vm.swappiness = 10\nnet.core.default_qdisc = fq\nnet.ipv4.tcp_congestion_control = bbr\n' >/etc/sysctl.d/90-vkus.conf
sysctl --system
ufw default deny incoming && ufw allow 22/tcp && ufw allow 80/tcp && ufw allow 443/tcp && ufw enable
printf 'PermitRootLogin prohibit-password\nPasswordAuthentication no\nKbdInteractiveAuthentication no\n' \
  >/etc/ssh/sshd_config.d/00-hardening.conf   # сначала положить свой ключ в authorized_keys
sshd -t && systemctl reload ssh
printf '[DEFAULT]\nbackend = systemd\nbanaction = ufw\n\n[sshd]\nenabled = true\nmode = normal\n' >/etc/fail2ban/jail.local
systemctl restart fail2ban
printf '{ "log-driver": "local", "log-opts": { "max-size": "10m", "max-file": "3" } }\n' >/etc/docker/daemon.json
systemctl restart docker
```

Для SSH `ufw allow`, а не `ufw limit`, и `fail2ban` в режиме `normal`, а не
`aggressive`: `ssh-keyscan` в GitHub Actions открывает пять соединений подряд,
и строгие правила банят раннер выкладки.

### 2. Код

```bash
su - deploy
git clone https://github.com/PixelShino/vkusnayakompania-landing.git /srv/vkus/site
cd /srv/vkus/site && pnpm install --frozen-lockfile
```

### 3. Directus

```bash
cd /srv/vkus/site/directus
cp .env.example .env
```

В `.env`: `SECRET` (`openssl rand -hex 32`), `PUBLIC_URL=https://admin.vkus-com.ru`,
`DB_PASSWORD`, `ADMIN_EMAIL` (настоящий адрес с обычным доменом: `.local` и
подобные Directus не принимает при входе), `ADMIN_PASSWORD`, блок SMTP
(`EMAIL_TRANSPORT=smtp` и данные почтового сервиса — без него не уйдут
приглашения и сброс пароля). `DIRECTUS_PORT` оставьте 8055.

```bash
docker compose up -d
curl -s http://127.0.0.1:8055/server/ping        # pong
docker compose cp snapshot.yaml directus:/directus/snapshot.yaml
docker compose exec -T directus node /directus/cli.js schema apply --yes /directus/snapshot.yaml
# … INFO: Snapshot applied successfully
```

Расширения из `directus/extensions/` контейнер читает с диска; после `git pull`
с новым или изменённым расширением — `docker compose restart directus`
(в логе `Loaded extensions: directus-extension-build-status, directus-extension-delivery, directus-extension-notify, directus-extension-optimize-upload, directus-extension-order-guard, directus-extension-pay, directus-extension-request-guard`).

Снапшот схемы лежит в репо (`directus/snapshot.yaml`), контейнер его не видит,
поэтому файл сначала копируется внутрь. CLI зовётся через `node /directus/cli.js`:
`npx directus` в образе не находит бинарник и качает пакет из npm заново.

Дальше роли, сборщик и Flow одним скриптом. Нужен статический токен
администратора: в админке «Пользователи → админ → Token → Generate», сохранить.

```bash
cd /srv/vkus/site
DIRECTUS_URL=http://127.0.0.1:8055 DIRECTUS_ADMIN_TOKEN=<токен админа> \
REBUILD_HOOK_URL=https://admin.vkus-com.ru/hooks/rebuild REBUILD_HOOK_SECRET=<секрет вебхука> \
pnpm setup
```

Скрипт напечатает `DIRECTUS_TOKEN` сборщика — он нужен в следующем шаге и
больше не показывается. Секрет вебхука придумайте сами (`openssl rand -hex 24`).
Адрес вебхука — публичный: Flow выполняется внутри контейнера Directus, и
`127.0.0.1:9000` там указывает на сам контейнер, а не на сервер.

Имя проекта, цвет и русский язык админки (в том числе на странице входа) ставит
тот же скрипт. Дальше в админке создайте пользователей редакторов с ролью
«Редактор» («Пользователи → +», роль «Редактор», приглашение уйдёт письмом).

### 4. Сайт

```bash
cd /srv/vkus/site
cp .env.example .env
```

В `.env`: `DIRECTUS_URL=http://127.0.0.1:8055`, `DIRECTUS_TOKEN=<токен сборщика>`,
`PUBLIC_YANDEX_MAPS_KEY=<ключ JS API Яндекс Карт>`, `SITE=https://vkus-com.ru`,
`PUBLIC_DIRECTUS_URL=https://admin.vkus-com.ru` (куда корзина отправляет заказ,
см. «Каталог доставки и заказы»).

Первый контент: сайт не соберётся без телефона, двух точек, пяти направлений,
фото первого экрана и SEO-полей (см. `pnpm test`). У точки есть своё поле
«Телефон точки»: пустое — на странице стоит общий номер из «Настроек». Заполните «Настройки»,
«Главная», «Точки» и «Направления» в админке — либо загрузите стартовый набор
из фикстуры: `pnpm exec node scripts/import-fixture.mjs` (заводит записи и
файлы из `src/data/fixture.json`, существующее не трогает; фото там
заглушки, их заменяют редакторы).

```bash
deploy/build.sh        # первый релиз, /srv/vkus/current появился
```

### 5. nginx и сертификаты

Конфиги из репо ссылаются на сертификаты, которых ещё нет, и с ними `nginx -t`
не проходит. Поэтому сначала временный блок на `:80` для выпуска, потом конфиги:

```bash
cat >/etc/nginx/sites-enabled/acme <<'EOF'
server { listen 80; server_name vkus-com.ru www.vkus-com.ru admin.vkus-com.ru; return 404; }
EOF
nginx -t && systemctl reload nginx
certbot certonly --nginx -d vkus-com.ru -d www.vkus-com.ru
certbot certonly --nginx -d admin.vkus-com.ru
rm /etc/nginx/sites-enabled/acme /etc/nginx/sites-enabled/default
cp deploy/nginx/10-vkus-tuning.conf /etc/nginx/conf.d/
cp deploy/nginx/vkus-com.ru.conf /etc/nginx/sites-available/vkus-com.ru
cp deploy/nginx/admin.vkus-com.ru.conf /etc/nginx/sites-available/admin.vkus-com.ru
ln -s /etc/nginx/sites-available/vkus-com.ru /etc/nginx/sites-enabled/
ln -s /etc/nginx/sites-available/admin.vkus-com.ru /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
```

Certbot сам добавит таймер продления.

Кеш дескрипторов (`open_file_cache`) выключен намеренно: релиз переключается
симлинком `current`, а с кешем nginx до двух минут отдавал `index.html`
прошлого релиза и помнил `404` на файлы, которые уже появились. Страница и
`/media/` отдаются с `Cache-Control: no-cache`: браузер перепроверяет их при
каждом заходе (неизменённые — одним `304`), поэтому правка видна сразу, а
адреса документов не меняются при замене файла.

Прокси для сборки. Directus не отвечает `304` на повторный запрос картинки, и
Astro при каждой сборке заново пережимает все фото: минута вместо нескольких
секунд. Локальный nginx на `127.0.0.1:8056` сверяет `If-Modified-Since` и
отдаёт `304`, если файл не менялся; сборка ходит в Directus через него:

```bash
mkdir -p /var/cache/nginx/directus-assets && chown www-data: /var/cache/nginx/directus-assets
cp deploy/nginx/directus-build.conf /etc/nginx/sites-available/directus-build
ln -s /etc/nginx/sites-available/directus-build /etc/nginx/sites-enabled/
nginx -t && systemctl reload nginx
sed -i 's|^DIRECTUS_URL=.*|DIRECTUS_URL=http://127.0.0.1:8056|' /srv/vkus/site/.env
```

### 6. Приёмник вебхука

`hooks.json` берёт секрет из окружения, поэтому `webhook` запускается с
флагом `-template`. Юнит из пакета Ubuntu стартует только при наличии
`/etc/webhook.conf` — условие снимается пустым `ConditionPathExists=`.
`-verbose` пишет вывод сборки в журнал: `journalctl -u webhook`.

```bash
cat >/etc/default/webhook <<'EOF'
HOOK_SECRET=<секрет вебхука, тот же что в pnpm setup>
EOF
chmod 600 /etc/default/webhook
mkdir -p /etc/systemd/system/webhook.service.d
cat >/etc/systemd/system/webhook.service.d/override.conf <<'EOF'
[Unit]
ConditionPathExists=

[Service]
User=deploy
EnvironmentFile=/etc/default/webhook
ExecStart=
ExecStart=/usr/bin/webhook -verbose -nopanic -template -ip 127.0.0.1 -port 9000 -hooks /srv/vkus/site/deploy/webhook/hooks.json
EOF
systemctl daemon-reload && systemctl enable --now webhook
curl -s -X POST -H 'X-Hook-Secret: <секрет>' http://127.0.0.1:9000/hooks/rebuild   # принято, сборка запущена
```

### 8. Выкладка кода из GitHub

В репозитории: `Settings → Secrets and variables → Actions`: переменная
`VPS_HOST` (IP или домен) и секрет `VPS_SSH_KEY` (приватный ключ, публичный —
в `/home/deploy/.ssh/authorized_keys`). После этого пуш в `main` собирает сайт
на сервере. Пока переменной нет, workflow пропускается.

Ключ стоит ограничить одной командой выкладки: даже утёкший, он не даст
шелла на сервере.

```
command="cd /srv/vkus/site && git pull --ff-only && deploy/build.sh",restrict ssh-ed25519 AAAA… github-actions
```

### 9. Проверка

1. В админке измените заголовок афиши и сохраните.
2. В «Публикации сайта» пойдёт полоса «Идёт сборка». Когда она дойдёт до
   конца, страница сама сменится на «Опубликовано», в колокольчике появится
   «Ваши правки опубликованы: 1 событие афиши», а `https://vkus-com.ru`
   покажет новый заголовок.
3. `ls -la /srv/vkus/current` указывает на свежий релиз; вывод сборки —
   `journalctl -u webhook`.

## Эксплуатация

- **Статус сборки**: в админке «Публикация сайта»; при ошибке там же хвост лога.
  «Есть правки, которых нет на сайте» дольше пяти минут — смотреть
  `/srv/vkus/watch.log` и `journalctl -u webhook`.
- **Сжатие загрузок**: строки `optimize-upload:` в логе Directus; «не сжат» —
  файл оставлен как загружен, сайт всё равно пережмёт его на сборке.
- **Логи**: `docker compose -f /srv/vkus/site/directus/docker-compose.yml logs -f directus`;
  ночные сборки — `/srv/vkus/build.log`; сборки после сохранения — `journalctl -u webhook`.
- **Пересобрать руками**: `sudo -u deploy /srv/vkus/site/deploy/build.sh`.
- **Обновить Directus**: поменять тег образа в `directus/docker-compose.yml`,
  `docker compose pull && docker compose up -d`. Перед этим бэкап.
- **Бэкап**: `deploy/backup.sh` (крон делает ночью). Восстановление:
  `gunzip -c /srv/backups/db-<дата>.sql.gz | docker compose exec -T database psql -U directus directus`
  и распаковать `uploads-<дата>.tar.gz` в `directus/`.
- **Схема поменялась** (новое поле): изменить в локальном Directus, выгрузить
  `GET /schema/snapshot?export=yaml` в `directus/snapshot.yaml`, закоммитить,
  на сервере — строго в таком порядке:
  1. `schema apply` из шага 3;
  2. сбросить кеш схемы: `curl -X POST -H "Authorization: Bearer <admin>" \
     http://127.0.0.1:8055/utils/cache/clear?system` или
     `docker compose restart directus`. CLI работает отдельным процессом, а
     кеш схемы у запущенного Directus в памяти: до сброса новая коллекция для
     API «не существует» (`FORBIDDEN`);
  3. `node scripts/directus-setup.mjs` (`pnpm setup`) — права редактора и
     сборщика на новую коллекцию, её место в Flow; дописывает только недостающее;
  4. `sudo -u deploy deploy/build.sh` — иначе сайт соберётся только по
     следующей правке или по сторожу.
- **Токены**: сборщика — в `/srv/vkus/site/.env` и в переменных Vercel;
  секрет вебхука — в `/etc/default/webhook` и в Flow «Пересборка сайта».
  Отозвать токен сборщика: «Пользователи → Сборщик сайта → Token».
- **Оповещения о заказах** (почта, Telegram через ретранслятор на seochron с 23.10.2026, кнопки статуса под
  заказом в чате и «Журнал статусов», журнал, `POST /notify/test`, включение SMTP): [NOTIFY.md](NOTIFY.md).

## Редактору: почему не вижу правку на сайте

Сначала откройте «Публикацию сайта». Если там идёт полоса, правка едет:
подождите, страница обновится сама. Если там «Опубликовано», прочитайте «Что
на сайте»: в нём перечислено всё, что сохранено, но не показывается.
Дальше по порядку:

1. **Черновик.** На сайт попадает только статус «Опубликовано». Если у
   записи «Черновик», вверху карточки висит жёлтая плашка «Черновик — блюдо не
   попадёт на сайт», а после сборки об этом скажет и колокольчик. Новое блюдо
   в «Блюдах» по умолчанию сразу «Опубликовано». В тортах, акциях, афише и
   меню новая запись по-прежнему создаётся черновиком (акцию и событие удобно
   готовить заранее), поэтому перед сохранением смотрите на статус.
2. **«Есть в наличии».** Блюдо без этой галочки остаётся на сайте серым в
   конце раздела, и заказать его нельзя. Скрытый раздел (черновик или архив)
   прячет и все свои блюда. Блюдо без цены на сайт не попадает.
3. **Даты показа.** Акция и событие афиши видны только между «Показывать с»
   и «Показывать по», включительно. В «Что на сайте» такие записи
   перечислены как «Вне дат показа». Ночная сборка в 00:10 включает и
   выключает их сама. Акция, где упомянуто приложение, на сайт не выходит
   (см. «Акции»).
4. **Идёт сборка.** Сборка занимает 10–30 секунд, с новыми фото до минуты.
   Правка, сохранённая во время сборки, уходит следующей сборкой сразу
   следом. «Ошибка сборки» значит, что на сайте осталась прежняя версия:
   перешлите разработчику текст из «Что пошло не так».
5. **Кеш браузера.** Если на сайте всё ещё старое, обновите страницу: на
   компьютере Ctrl+F5 (Cmd+Shift+R на Mac), на телефоне потяните страницу
   вниз. Можно открыть сайт в режиме инкогнито. Фото и меню отдаются без
   долгого кеша, но браузер мог открыть вкладку из памяти.

## Оповещения и ход сборки: выкатка на прод

1. `git pull`, затем `docker compose restart directus`. В логе должно быть
   `Loaded extensions: directus-extension-build-status, directus-extension-notify, …`.
2. `schema apply` по `directus/snapshot.yaml`, затем сброс кеша схемы. Схема
   добавляет «Оповещения», «Журнал оповещений», поле «Оповещения» у заказов и
   заявок, `progress`/`step` у «Публикации сайта», плашки «Черновик» у восьми
   коллекций и `published` по умолчанию у `products.status`. Сборка между
   `git pull` и `schema apply` пройдёт, но не запишет свой статус
   (`статус сборки не записан: 400`): нового поля ещё нет.
3. `pnpm setup`. Редактору даются «Оповещения» без токена бота и журнал на
   чтение, сборщику — уведомления и роли пользователей для колокольчика.
4. `sudo -u deploy deploy/build.sh`. Первая сборка создаёт отметку
   `/srv/vkus/published-since`, уведомления «Ваши правки опубликованы»
   начинаются со следующей.
5. «Оповещения»: адреса, бот, чаты, затем `POST /notify/test` (см. [NOTIFY.md](NOTIFY.md)).

## Каталог доставки и заказы

Страница `/catalog/` — каталог доставки на сайте, перенесённый импортом из
магазина FoodPicasso (`vkusdostavka.shop`): 13 разделов, около 120 блюд. С
12.10.2026 каталог на сайте и есть магазин: страницы не ссылаются ни на
приложение, ни на `vkusdostavka.shop`. Гость собирает
корзину, оставляет имя и телефон — заказ падает в админку, менеджер перезванивает
и подтверждает состав, адрес и время. С 22.10.2026 (решение владельца) заказ
с сайта оплачивается только онлайн картой (см. «Онлайн-оплата»): блюда и
доставка одним платежом. Стоимость доставки считается по зоне, в которую
попадает адрес (см. «Доставка по зонам»); если адрес не нашёлся на карте,
её называют при звонке и берут при доставке.

**Коллекции** (группа «Каталог доставки»):

| Коллекция | Что | Кто правит |
|---|---|---|
| `product_categories` «Разделы» | название, адрес раздела (`slug`), порядок, статус | редактор |
| `products` «Блюда» | раздел, название, цена и старая цена, вес, размеры (`variants`: название, вес, цена), начинки на выбор (`fillings`), фото с alt, описание, состав, «В наличии», «Хит» / «Новинка», статус, порядок | редактор |
| `orders` «Заказы» | номер, статус (новый → в работе → выполнен / отменён), имя, телефон, доставка с адресом (с 23.10.2026 по пунктам: улица и дом, квартира / офис, подъезд, этаж, код домофона) или самовывоз с точкой, зона и стоимость доставки, время, комментарий, строки и сумма, к оплате, источник, заметка менеджера | редактор (без удаления); сайт — только создание |

- **Нет в наличии** — снять галочку «В наличии»: блюдо остаётся на сайте серым
  в конце раздела, в корзину не кладётся, а у тех, у кого оно уже в корзине,
  заказ не уйдёт, пока его не уберут. **Скрыть совсем** — статус «Черновик»
  или «Архив». Скрытый раздел прячет и все свои блюда.
- **Размеры** — список «Размеры» в блюде: у каждого своя цена. Один размер
  сайт сворачивает в цену блюда. **Начинки** — теги «Начинки на выбор»: гость
  обязан выбрать одну, иначе торт не добавить; цена от начинки не зависит.
- Пустые разделы и блюда без цены на сайт не попадают (сборка пишет
  предупреждение). Без фото блюдо встаёт с плашкой «Фото скоро».
- Каталог необязателен: если коллекций нет или они пусты, сайт собирается
  как раньше, страница каталога показывает «Каталог обновляется» и закрыта от
  индексации, а ссылки «Доставка» ведут в магазин.

**Заказы в админке.** Список «Заказы» открывается новыми сверху, закладки
«Новые» и «В работе». В карточке заказа, пока статус «Новый», вверху
подсказка: «Гость ждёт звонка. Позвоните, подтвердите состав, сумму, адрес и
время — и переведите заказ в „В работе“»; у заказа, оплаченного на сайте, её
место занимает «Оплачен картой на сайте — сумму с гостем обсуждать не нужно». Каждый новый заказ с сайта приходит уведомлением
(колокольчик в админке) всем активным пользователям с ролями «Administrator» и
«Редактор»; письмом — только когда настроен SMTP. Заказ, принятый по телефону,
редактор заводит сам («Источник: телефон»).

**Защита заказа.** Публичная роль может только *создать* заказ и не может
прочитать ни один, в том числе свой. Расширение
`directus/extensions/order-guard` проверяет заказ до записи: имя, российский
телефон, согласие, адрес или точку; строки собирает заново из `products` по
текущим ценам (браузер называет только блюдо, размер, начинку и количество),
сумму считает само, статус «Новый» и источник «Сайт» ставит само. Если цена
в админке поменялась после сборки сайта, в «Заметке менеджера» будет «На сайте
гость видел …, по текущим ценам …». Не больше 6 заказов за 10 минут с одного
адреса; адрес берётся из `X-Forwarded-For` nginx при `IP_TRUST_PROXY=1`
(в `docker-compose.yml`), подставить чужой адрес в начало заголовка нельзя.
Правила хука и формы на сайте одни и те же (`src/lib/order.ts`), паритет
телефона и веса проверяет `pnpm test`.

**Откуда браузер шлёт заказ.** Корзина отправляет `POST <PUBLIC_DIRECTUS_URL>/items/orders`
прямо из браузера, поэтому Directus должен разрешить сайту CORS:

```env
# directus/.env
CORS_ORIGIN=https://vkus-com.ru,https://www.vkus-com.ru   # это и есть значение по умолчанию
```

```env
# .env сайта (и переменные Vercel, если превью должно принимать заказы)
PUBLIC_DIRECTUS_URL=https://admin.vkus-com.ru
```

Без `PUBLIC_DIRECTUS_URL` корзина работает, но вместо формы предлагает
оформить заказ в магазине или по телефону. Превью на Vercel с чужим доменом
заказы не отправит, пока его адрес не добавлен в `CORS_ORIGIN` — так и задумано.

**Импорт из магазина.** У FoodPicasso нет открытого API, поэтому
`scripts/import-catalog.mjs` читает HTML страниц разделов `vkusdostavka.shop`:
блюда — блоки `.ddish` с `data-id`, `data-prices` (рубли × 10 000: `6850000` —
это 685 ₽), `data-modifiers` (размеры и начинки), `data-media` (фото);
«стоп-лист» — класс `ddish--stop`. Фото берутся в исходном размере с CDN
магазина и грузятся через `/files/import` в папку «Каталог» (дальше их ужимает
`optimize-upload`). Связка записи с магазином — поле `source_id`.

```bash
DIRECTUS_URL=http://127.0.0.1:8055 DIRECTUS_ADMIN_TOKEN=<токен админа> \
  node scripts/import-catalog.mjs --dry-run     # что изменится, без записи
node scripts/import-catalog.mjs                 # первый импорт: заводит недостающее, существующее не трогает
node scripts/import-catalog.mjs --sync          # сверить с магазином: цены, веса, наличие, размеры; пропавшие блюда — в архив
```

Флаги: `--no-photos` (без фото), `--save file.json` (сохранить разбор),
`--from file.json` (импорт из сохранённого разбора, без сети), `SHOP_URL` —
другой адрес магазина. Повторный запуск без изменений в магазине ничего не
меняет. Обычный импорт не перезаписывает правки редактора (только дозагружает
фото блюдам без фото); `--sync` переписывает поля магазина (название,
описание, цену, вес, размеры, начинки, наличие, бейджи, раздел, порядок) и
только там, где они разошлись, а фото, alt, слаг и состав оставляет. Блюдо,
которое снова появилось в магазине, `--sync` возвращает из архива; черновики
не трогает. Скрыть блюдо навсегда, несмотря на магазин, — статус «Черновик».

**Выкатка каталога на прод** — строго по порядку:

1. `git pull` на сервере, `docker compose restart directus` — подхватить
   `order-guard` и новые `CORS_ORIGIN` / `IP_TRUST_PROXY` (для env нужен
   `docker compose up -d directus`, простой `restart` их не перечитывает);
2. `schema apply` из шага 3 (`directus/snapshot.yaml`);
3. сброс кеша схемы (`/utils/cache/clear?system` или `restart directus`);
4. `pnpm setup` — права редактора на разделы, блюда и заказы, публичное
   «только создание» заказа, закладки, Flow на `product_categories` и `products`;
5. импорт каталога: `node scripts/import-catalog.mjs` с `DIRECTUS_URL` и токеном
   админа сервера (через туннель или на самом сервере);
6. `PUBLIC_DIRECTUS_URL=https://admin.vkus-com.ru` в `/srv/vkus/site/.env`;
7. `sudo -u deploy deploy/build.sh` и проверка: `/catalog/`, тестовый заказ,
   уведомление в админке, удалить тестовый заказ.

## Онлайн-оплата (ЮKassa)

С 19.10.2026 заказ из корзины можно оплатить картой на сайте. С 20.10.2026
(решение владельца, подана заявка «Платежи на сайте») банк — **ЮKassa**.
Интернет-эквайринг Альфа-Банка (шлюз RBS, REST) с 21.10.2026 снят с выбора
в админке (решение владельца: «пока что»); провайдер
`directus/extensions/pay/providers/alfa.js` и его поля остались в коде, в
дропдауне «Банк» их нет (вернуть — `choice('Альфа-Банк', 'alfa')` в
`scripts/setup/payments.mjs` и в `directus/snapshot.yaml`). С 22.10.2026
(решение владельца: «Через сайт оплата только онлайн… Оплата доставки тоже
сразу онлайн») заказ с сайта оплачивается только онлайн — блюда вместе с
доставкой по зоне (см. «Доставка по зонам»); так написаны и документы
`/docs/offer/`, `/docs/delivery/`. Выключенная в админке оплата — запасной
режим, не обычный: сайт принимает заказ без оплаты, как до 19.10.2026, и
об оплате менеджер договаривается при звонке, а документы этот режим не
описывают.

**Что видит гость.** В оформлении после «Когда» — блок «Оплата» с одним
вариантом «Онлайн картой». Вариант «При получении» с 21.10.2026
закомментирован в `src/components/catalog/PayChoice.astro` (решение
владельца: не просили; с 22.10.2026 — «через сайт оплата только онлайн»),
как и кнопка «Оплачу при получении» в `PayStep.astro`;
скрипт, настройка «при получении» в админке и `POST /pay/offline` остались —
раскомментировать разметку, и выбор вернётся. Подпись под «Онлайн картой»:
«…на защищённой странице ЮKassa» (текст из «Оплаты», пустое поле — текст по
умолчанию). Кнопка внизу говорит «Перейти к оплате». Заказ сначала
сохраняется в админке, потом браузер просит у Directus ссылку на страницу
оплаты и уходит на неё. После оплаты банк возвращает гостя на
`/catalog/?pay=ok|fail|wait&order=…`, там открывается корзина с экраном
итога:

| Экран | Когда | Что можно сделать |
|---|---|---|
| «Заказ оплачен» | банк подтвердил платёж | вернуться в каталог |
| «Оплата не прошла» | отказ банка, истекло время, гость ушёл со страницы банка | «Оплатить ещё раз» (живая ссылка выдаётся та же, мёртвая — новая); «Оплачу при получении» закомментирована с 21.10.2026 |
| «Оплата не прошла» · «Банк подтвердил меньшую сумму» | банк подтвердил меньше, чем «к оплате» в заказе (счёт вырос после выдачи ссылки или сумму подменили): заказ **не** «Оплачен», а «Не прошла» с громкой строкой в журнале и уведомлением менеджерам «сверьте»; повтор уведомления банка ничего не добавляет | «Оплатить ещё раз» отвечает «позвоните нам» — второй платёж сверху не открывается, разницу менеджер решает по телефону |
| «Оплата не открылась» | банк не ответил или ответил ошибкой, тайм-аут | то же |
| «Проверяем оплату» | банк ещё подтверждает (3-D Secure) | страница сама спрашивает статус 45 секунд |
| «Заказ ждёт оплаты» | гость нажал «назад» на странице банка или вернулся во вкладку | «Перейти к оплате»; «Оплачу при получении» закомментирована с 21.10.2026 |

Заказ на этих экранах не теряется: номер, телефон, строки и сумма лежат в
`localStorage` (`vk-pay-v1`) двое суток. Перезагрузка страницы итог второй
раз не показывает — адрес очищается.

**Тестовый режим.** Пока в «Оплате» стоит «Тест», гости блока «Оплата» не
видят. Проверяющий открывает `https://vkus-com.ru/catalog/?paytest=1` — это
устройство видит онлайн-оплату с ярлыком «тест» (`?paytest=0` снимает).
Провайдер «Заглушка» — своя страница «Оплатить / Отклонить / Вернуться в
магазин» без банка; работает только в тестовом режиме, в боевом выключается
сама.

**Как устроено.** Расширение `directus/extensions/pay` — бандл из эндпоинта и
хука, без сборки.

| Адрес | Что делает |
|---|---|
| `GET /pay/config` | включена ли оплата, разрешено ли «при получении», тексты для гостя; без секретов |
| `POST /pay/start` `{number, phone, path}` | находит заказ по номеру и телефону (сайт не читает заказы, так гость доказывает, что заказ его), проверяет: не старше двух суток, не закрыт, не оплачен; создаёт платёж в банке → `{url}`; повтор при живой ссылке отдаёт ту же |
| `POST /pay/offline` | гость передумал: «при получении» (кнопка на сайте с 21.10.2026 закомментирована) |
| `POST /pay/status` | статус оплаты; ждущий уточняется у банка |
| `GET /pay/return?o=<id>&t=<ключ>` | сюда банк возвращает гостя: статус спрашивается у банка заново, гость уходит на сайт с итогом; `t` — неугадываемый ключ попытки |
| `POST /pay/yookassa/webhook` | уведомление ЮKassa: статус перепроверяется запросом к ЮKassa |
| `GET/POST /pay/callback` | уведомление Альфы: подпись `checksum` (HMAC-SHA256 по ключу), статус всё равно берётся у банка |
| `GET /pay/check` | только администратор: действующие настройки без секретов и пробный запрос к банку |
| `GET /pay/mock/<id>` | страница заглушки, только тест |

Раз в пять минут хук спрашивает у банка все «Ждём оплату» за трое суток;
ссылку, которая умерла полчаса назад, переводит в «Не прошла». Сумма — из
`orders.to_pay` (блюда − скидка именинника − баллы + доставка по зоне, см.
«Доставка по зонам») или `orders.total`, в копейках; состав для чека — из
строк заказа, платная доставка — отдельной строкой «Доставка». Номер
попытки для банка — `1910-4821-57` (номер, id записи), повтор —
`1910-4821-57r2`: у Альфы это номер заказа в банке, у ЮKassa он лежит в
`metadata.bank_order` рядом с `order_id` и `order_number`.

**Поля заказа** (блок после суммы, только чтение, пишет только сервер — хук
вырезает их из правок людей и из заказа с сайта):

| Поле | Значения |
|---|---|
| `payment_status` «Оплата» | — · Ждём оплату · Оплачен · Не прошла · Возврат |
| `payment_method` «Способ оплаты» | Онлайн картой · При получении (его может поменять редактор) |
| `paid_at` «Оплачен» | время подтверждения банком |
| `payment_id` «Номер в банке» | id платежа ЮKassa или номер заказа Альфы: по нему платёж ищут в кабинете |
| `payment_url` «Ссылка на оплату» | пока ждёт — можно отправить гостю |
| `payment_log` «Журнал оплаты» | «20.10 16:35 — ссылка на оплату 1 535 ₽ (ЮKassa, бой)», «— оплачено 1 535 ₽; уведомление ЮKassa (payment.succeeded)», «— частичный возврат: всего вернули 200 ₽» |
| `payment_meta` | скрытое: попытка, адрес возврата, номера банка, ключи возврата |

Если за один заказ оплачены две попытки (две вкладки), журнал скажет
«ВНИМАНИЕ: оплачена ещё одна попытка … — лишнее верните в кабинете банка».

В списке заказов колонка «Оплата» сразу за статусом, закладки «Оплачены» и
«Ждут оплату». Оплаченный заказ показывает зелёную подсказку «сумму с гостем
обсуждать не нужно», подсказка «гость ждёт звонка» у него прячется. Об оплате
приходит уведомление (колокольчик) администраторам и редакторам. Изменение
статуса идёт через `ItemsService`: другие хуки видят `orders.items.update` с
`payment_status: 'paid'`. В тестовом режиме («Тест», заглушка или тестовый
магазин) журнал и уведомление начинаются с «ТЕСТ, денег не списано» — тестовое
«оплачено» не спутать с настоящим. Каждый обработчик (`status`, возврат гостя,
уведомления банка, расписание) перечитывает заказ уже под блокировкой: снимок,
снятый до ответа банка, не затирает запись соседнего обработчика.

**Настройки** — «Каталог доставки → Оплата» (`payment_settings`, одна запись):
онлайн-оплата вкл/выкл, «при получении» вкл/выкл (на сайте вариант сейчас
закомментирован), банк (ЮKassa / заглушка), режим; для ЮKassa — `shopId` и
секретный ключ (скрыт маской) с подсказкой про уведомления; поля Альфы
(логин и пароль API или токен, шлюзы теста и боя, ключ уведомлений) в базе
остались, но скрыты — банк больше не выбирается;
адрес сайта, сколько живёт страница оплаты, чек (передавать состав, СНО,
НДС, способ расчёта, предмет расчёта, ФФД), пять текстов для гостя.
Редактор видит всё, кроме секретов, и может включить/выключить оплату и
поменять тексты; ключи, логины и режим — только администратор.

Переменные окружения Directus важнее полей админки (тогда секреты не
попадают в базу и бэкапы): `PAY_ENABLED`, `PAY_MODE` (`test`/`prod`),
`PAY_PROVIDER` (`yookassa`/`alfa`/`mock`), `PAY_YOOKASSA_SHOP_ID`,
`PAY_YOOKASSA_SECRET_KEY`, `PAY_ALFA_LOGIN`, `PAY_ALFA_PASSWORD`,
`PAY_ALFA_TOKEN`, `PAY_ALFA_GATEWAY`, `PAY_CALLBACK_KEY`, `PAY_SITE_URL`.
`PAY_YOOKASSA_API` — только для проверки на поддельной ЮKassa, действует
лишь в тестовом режиме, на сервере пусто. Их пробрасывает
`docker-compose.yml`; после правки `.env` — `docker compose up -d directus`.

**nginx** менять не нужно: `/pay/*` идёт через `admin.vkus-com.ru` тем же
`location /`, что и вся админка. Банки шлют уведомления только на HTTPS с
доверенным сертификатом — у `admin.vkus-com.ru` он есть (Let's Encrypt).
`PUBLIC_URL` Directus должен быть `https://admin.vkus-com.ru`: из него
собираются адреса возврата и уведомлений.

### ЮKassa

- **Платёж** — `POST https://api.yookassa.ru/v3/payments`, Basic
  `shopId:секретный ключ`, `Idempotence-Key` на каждый запрос: одностадийный
  (`capture: true`), `confirmation: redirect` с `return_url` на
  `/pay/return`, `description` «Заказ 1910-4821, Вкусная компания»,
  `metadata` с заказом. Молчание или 500 — один повтор с тем же ключом
  (второй платёж не создастся), тайм-аут 10 секунд на круг.
- **Статус** — `GET /v3/payments/{id}`: `succeeded` → «Оплачен» (полный
  возврат → «Возврат», частичный — строка в журнале), `canceled` → «Не
  прошла» с причиной словами («на карте не хватает денег», «время на
  оплату истекло»…), `pending` → ждём; при возвращении гостя `pending`
  значит «ушёл со страницы ЮKassa». `waiting_for_capture` при одностадийном
  платеже не бывает; если пришёл — провайдер списывает его сам.
- **Ждущий платёж ЮKassa магазин отменить не может**, поэтому «Оплатить ещё
  раз» отдаёт ту же страницу, пока ЮKassa её держит, — второй платёж за
  заказ не создаётся.
- **Уведомления** — `POST https://admin.vkus-com.ru/pay/yookassa/webhook`,
  события `payment.succeeded`, `payment.canceled`, `refund.succeeded`.
  Тело ничего не решает: статус спрашивается у ЮKassa, заказ ищется по id
  платежа или по `metadata`, которую вернула сама ЮKassa. Поддельное
  «оплачен» не меняет ничего, повтор безвреден, чужой или незнакомый платёж
  — 200 и запись в лог, ЮKassa недоступна — 503 (ЮKassa повторяет
  уведомление сутки). Адреса ЮKassa (`185.71.76.0/27`, `185.71.77.0/27`,
  `77.75.153.0/25`, `77.75.156.11`, `77.75.156.35`, `77.75.154.128/25`,
  `2a02:5180::/32`) не ограничиваются, остальные — 40 запросов за 10 минут.
- **Чек 54-ФЗ** («Чек» включён): `receipt` из строк заказа и, если доставка
  платная, строки «Доставка» (`payment_subject: service`) — цена за
  единицу, `vat_code`, `payment_mode`, `payment_subject`, `measure: piece`
  (ФФД 1.2), `tax_system_code`, `customer.phone`. Баллы и скидка именинника
  раскладываются по строкам пропорционально, чек сходится с оплатой до
  копейки. Коды из админки переводятся: НДС «без» → 1, 0 % → 2, 10 % → 3,
  5 % → 7, 7 % → 8, 22 % → 11; СНО ОСН → 1, УСН «доходы» → 2 … патент → 6.
  **«Чеки от ЮKassa» доставляют чек только на почту, а в форме заказа почты
  нет** — с ними нужна доработка (поле «Почта для чека»); с онлайн-кассой
  через ЮKassa (АТОЛ, «Бизнес.Ру» и др.) телефона достаточно.
- **Тестовый магазин** — свой `shopId` и ключ `test_…`; платежи с
  `test: true`. Ключ `test_…` в режиме «Бой» выключает оплату, а платёж
  тестового магазина в бою не считается оплатой.
- **Возврат** — в кабинете ЮKassa («Платежи» → платёж → «Вернуть»):
  уведомление `refund.succeeded` переводит заказ в «Возврат» (или пишет
  частичный возврат в журнал). Кнопки возврата в админке нет.
- Сертификат `api.yookassa.ru` обычный (корневые сертификаты Node); с
  сервера Directus соединение проверено 20.10.2026.

**Что нужно от владельца для ЮKassa:**

1. Дождаться одобрения анкеты «Платежи на сайте» и подписать договор.
2. Кабинет ЮKassa → «Интеграция» → «Ключи API»: `shopId` и секретный ключ
   (`live_…`; выпустить, если его нет). Тестовый магазин (ключ `test_…`)
   заводится в кабинете сразу, без договора.
3. «Интеграция» → «HTTP-уведомления»: адрес
   `https://admin.vkus-com.ru/pay/yookassa/webhook`, события
   `payment.succeeded`, `payment.canceled`, `refund.succeeded` — для
   боевого и тестового магазина отдельно.
4. Чеки: «Чеки от ЮKassa» (нужна почта гостя — доработка формы) или
   онлайн-касса через ЮKassa; бухгалтеру — СНО, НДС (с 2026 — 22 %, на УСН
   5 % / 7 % или без НДС), способ расчёта и предмет расчёта — в «Оплату».
5. `shopId` и ключ — в `PAY_YOOKASSA_SHOP_ID` / `PAY_YOOKASSA_SECRET_KEY`
   в `directus/.env` на сервере (или в «Оплату»).

**Проверка на тестовом магазине ЮKassa:**

1. «Оплата»: банк «ЮKassa», режим «Тест», `shopId` и ключ `test_…`,
   онлайн-оплата вкл; «Проверить настройки и связь с банком» → «Ключ
   принят, магазин … — тестовый».
2. `https://vkus-com.ru/catalog/?paytest=1`, корзина, «Онлайн картой»,
   «Перейти к оплате» → страница ЮKassa.
3. Карта `5555 5555 5555 4477` (с 3-D Secure) или `5555 5555 5555 4444`,
   любой будущий срок и CVC → «Заказ оплачен», в журнале «оплачено …;
   возврат гостя» и уведомление ЮKassa.
4. Отказ: `5555 5555 5555 4592` (не пройден 3-D Secure) → «Оплата не
   прошла», «Оплатить ещё раз» открывает новую страницу.
5. Возврат в кабинете тестового магазина → заказ «Возврат».
6. Боевой ключ `live_…` → режим «Бой», заказ на 1–10 ₽ своей картой и его
   возврат в кабинете.

**Проверка без ЮKassa.** `PAY_YOOKASSA_API` направляет провайдер на
поддельную ЮKassa (только в тестовом режиме): так 20.10.2026 проверены
переход, оплата, отказ, «вернуться в магазин» и повтор той же страницы,
уведомления (поддельные, незнакомые, повторы, заморозка, частичный и
полный возврат, 503, лимиты) на настоящем Directus.

### Выкатка

**Первая выкатка оплаты на прод** — строго по порядку:

1. `git pull` на сервере, `docker compose up -d directus` (новые переменные
   `PAY_*` в `docker-compose.yml`), в логе `Loaded extensions: …, directus-extension-pay, …`;
2. `schema apply` из шага 3 (`directus/snapshot.yaml`), сброс кеша схемы;
3. `pnpm setup` — модуль `scripts/setup/payments.mjs` дозаводит «Оплату» и

5. «Оплата» → тест → проверка по списку выше; потом «Бой».

**Выкатка ЮKassa** (оплата уже на проде) — строго по порядку:

## Доставка по зонам (расширение delivery)

С 22.10.2026 (решение владельца: «оплата доставки тоже сразу онлайн, в
зависимости от зоны, бесплатная от 7000») стоимость доставки считается по
адресу. Гость в корзине выбирает дом из подсказок и сразу видит зону, цену
доставки и «К оплате»; при отправке сервер ещё раз находит зону по адресу,
считает стоимость, проверяет минимальный заказ и пишет всё в заказ. Онлайн
оплачиваются блюда и доставка одним платежом, в чеке ЮKassa доставка —
отдельная строка. Адрес не нашёлся на карте или он вне всех зон — заказ всё
равно принимается, доставку менеджер называет при звонке, как раньше.

**Зоны** — «Каталог доставки → Зоны доставки» (`delivery_zones`). Начальные
данные — зоны магазина FoodPicasso (`vkusdostavka.shop`, сняты 20.10.2026),
лежат в `src/data/delivery-zones.json`; `pnpm setup` заводит их только в
пустую коллекцию, поэтому цены, поменянные в админке, повторный запуск не
затирает.

| Зона (id магазина) | Доставка | Бесплатно от | Минимальный заказ |
|---|---|---|---|
| Рядом с нами — Советский, Промышленный, Октябрьский, Кировский (492128) | 400 ₽ | 7 000 ₽ | 1 000 ₽ |
| Центр — Ленинский, Самарский, Железнодорожный (492126) | 600 ₽ | 7 000 ₽ | 1 000 ₽ |
| Куйбышевский район — Волгарь, Сухая Самарка, 116-й километр (540164) | 1 000 ₽ | 10 000 ₽ | 1 000 ₽ |
| Красноглинский район, Зубчаниновка, Мехзавод, Крутые Ключи, Кошелев-Парк, Смышляевка (492131) | 1 000 ₽ | 10 000 ₽ | 2 500 ₽ |
| Дальние посёлки — Курумоч, Новосемейкино, Царевщина, Волжский (540159) | 2 500 ₽ | 30 000 ₽ | 1 000 ₽ |
| Новокуйбышевск (495935) | 4 000 ₽ | 170 000 ₽ | 2 500 ₽ |

| Поле | Что значит |
|---|---|
| «Статус» | «Действует» / «Выключена»: выключенная зона не считается, адрес в ней — «вне зон» |
| «Название» | так зону видят гость в корзине и менеджер в заказе |
| «Доставка, ₽» | цена; 0 — бесплатно всегда |
| «Бесплатно от, ₽» | от какой суммы блюд (до скидки и баллов) доставка бесплатна; пусто — бесплатной нет |
| «Минимальный заказ, ₽» | меньше — заказ с доставкой сюда не примем; 0 — без минимума |
| «Граница на карте» | полигон `[[долгота, широта], …]` из магазина; менять не нужно |

Если дом попадает в две зоны (Куйбышевский район — Волгарь, Сухая Самарка, 116-й километр и Новокуйбышевск на карте
магазина заходят друг на друга), берётся зона с меньшей ценой доставки.
Редактор меняет цены, пороги, название и статус; новые зоны и границы — у
администратора. Правка зоны пересобирает сайт (Flow «Пересборка сайта»).

**Как считается** (`directus/extensions/delivery/geo.js`, его же импортирует
`order-guard`):

- доставка = 0, если сумма блюд (`orders.total`, до скидки и баллов) не
  меньше «бесплатно от», иначе цена зоны;
- блюд меньше минимума зоны — заказ не принимается: «Минимальный заказ для
  доставки по этому адресу — 2 500 ₽, в корзине 1 800 ₽. Добавьте блюд или
  выберите самовывоз.»;
- «К оплате» (`to_pay`) теперь у **каждого** заказа с сайта: блюда − скидка
  именинника − баллы + доставка; онлайн-оплата просит у банка именно её;
- баллы начисляются и «сумма покупок» гостя считается от блюд, оплаченных
  деньгами (`total − discount − bonus_spent`), доставка — не покупка;
  списать баллами можно только часть блюд (30 %), доставку — нет;
- с 23.10.2026 (решение владельца) заказ, в котором списаны баллы
  (`bonus_spent > 0`), баллов не приносит: `reconcileOrder` не создаёт
  `accrual`, кабинет и корзина не обещают начисление за такой заказ.

**Поля заказа** (рядом с адресом):

| Поле | Значения |
|---|---|
| `address` «Адрес доставки» | улица и дом — только по ним сервер ищет зону; в админке в несколько строк, длинный адрес читается с телефона |
| `address_flat` «Квартира / офис», `address_entrance` «Подъезд», `address_floor` «Этаж», `address_intercom` «Код домофона» | с 23.10.2026, сразу под адресом; до 20 / 10 / 10 / 20 знаков (длиннее обрезается), пустое и у самовывоза — пусто |
| `address_details` «Квартира, подъезд, этаж (старое поле)» | одной строкой у заказов до 23.10.2026, видно только заполненным; от старой страницы сервер принимает его как раньше |
| `delivery_zone` «Зона доставки» | имя зоны; пусто — адрес не нашли или он вне зон |
| `delivery_cost` «Доставка, ₽» | 0 — бесплатно (и всегда у самовывоза); пусто — назвать при звонке, в «К оплате» не вошла |
| `to_pay` «К оплате, ₽» | блюда − скидка − баллы + доставка |
| `manager_note` | «Адрес не найден на карте — стоимость доставки назвать при звонке.» или «Адрес вне зон доставки — предложить самовывоз или назвать стоимость при звонке.» |

Уведомление менеджеру: «Доставка: улица Советской Армии, 177, Самара, кв. 12,
подъезд 2, этаж 5, домофон 12К · зона «Рядом с нами — …» · 400 ₽» (или
«бесплатно (от 7 000 ₽)», «стоимость назвать при звонке»), внизу «Итого
(блюда)» и «К оплате», в теме — «К оплате». Пустые пункты адреса пропускаются,
старое `address_details` дописывается в конец; письмо и Telegram собирают
адрес так же (`addressLine` в `notify/lib.js`).
Стоимость, которую менеджер вписал в заказ после звонка, «К оплате» не
меняет: эту доставку гость платит курьеру.

**Эндпоинт** `/delivery` (публичный, CORS как у всего Directus):

| Адрес | Что делает |
|---|---|
| `GET /delivery/suggest?q=…` | `{ items: [{ label: "улица Советской Армии, 177", city: "Самара", lat, lng }] }` — до 6 домов Самары и области на набранной улице, только с номером дома; меньше 3 знаков — пусто |
| `POST /delivery/quote` `{ address }` | `{ found: true, address: "улица Советской Армии, 177, Самара", lat, lng, zone: { id, name, price, free_from, min_order } }`; не нашли — `{ found: false }`; нашли, но вне зон — `{ found: false, outside: true, address, lat, lng }` |
| `GET /delivery/zones` | `{ items: [{ id, name, price, free_from, min_order }] }` — действующие зоны без полигонов, кэш 5 минут |

`suggest` и `quote` вместе — не больше 60 запросов в минуту с адреса, дальше
429 `{ error: 'rate', message }`. Корзина кладёт в поле адреса то, что
сервер узнает снова: подпись подсказки (в Самаре) или «Город, подпись»;
адрес без города сервер ищет в Самаре.

**Геокодер** — `directus/extensions/delivery/photon.js`, без ключей:

- **Photon** (`photon.komoot.io`): запрос в рамке Самарской агломерации
  (широта 52,9–53,6, долгота 49,7–50,7), только дома (`layer=house`), к
  адресу без города дописывается «Самара»; дом годится, если его номер есть в
  адресе и улица похожа на набранную (на мусор Photon отвечает похожей улицей —
  такой ответ отбрасывается);
- **Nominatim** — запасной, только для расчёта (подсказки им запрещены),
  когда Photon не ответил: не чаще раза в секунду на весь сервер;
- кэш в памяти по нормализованному адресу (нижний регистр, одиночные
  пробелы): сутки, до 2 000 записей; эндпоинт и `order-guard` делят один кэш,
  поэтому заказ по адресу, который корзина только что посчитала, геокодер не
  ждёт; тайм-аут 5 секунд; `User-Agent: vkus-com.ru (delivery)`;
- геокодер не ответил — «не нашли»: заказ не теряется, доставку назовут при
  звонке. Photon под нагрузкой отвечает 503 — это видно в логе строкой
  `order-guard: адрес «…» не проверен` или `delivery: подсказки … не получены`.

**Чек ЮKassa**: строки блюд на «К оплате» минус доставка (баллы и скидка
раскладываются только по блюдам) и строка «Доставка» на её стоимость с
признаком «услуга» (`payment_subject: service`); доставка 0 или пусто — чек
как раньше; если после доставки на блюда ничего не остаётся — одна строка
«Заказ …». Доставка в чеке берётся из самого «К оплате» (что счёт добавил к
блюдам), а не из поля, вписанного после звонка.

**Выкатка на прод** — строго по порядку (`order-guard` теперь импортирует
`../delivery/*.js`, а `loyalty` читает `delivery_cost`, поэтому схема — до
перезапуска):

1. `git pull` на сервере;
2. `schema apply` из шага 3 (`directus/snapshot.yaml`: коллекция
   `delivery_zones`, поля `orders.delivery_zone`, `orders.delivery_cost`,
   новые подсказки «Сумма» и «К оплате», порядок полей заказа);
3. сброс кеша схемы — `/utils/cache/clear?system`, **не** `restart`: после
   перезапуска новый `order-guard` до шага 4 пишет в заказ `to_pay`, на
   который у публичной роли ещё нет права, и заказы с сайта получают отказ;
4. `pnpm setup` — шесть зон из `src/data/delivery-zones.json` (если
   коллекция пуста), права редактора (чтение и цены) и сборщика (чтение) на
   зоны, `delivery_zone`, `delivery_cost`, `to_pay` в публичном и гостевом
   создании заказа, список зон, Flow; без этого шага публичный заказ получит
   отказ по правам на `to_pay`;
5. `docker compose restart directus` — в логе `Loaded extensions: …,
   directus-extension-delivery, …`;
6. проверка: `curl https://admin.vkus-com.ru/delivery/zones` — шесть зон;
   `curl -X POST -H 'Content-Type: application/json' -d '{"address":"Советской Армии 177"}' https://admin.vkus-com.ru/delivery/quote`
   — зона 400 ₽; тестовый заказ с доставкой — в админке зона, доставка и
   «К оплате»; удалить тестовый заказ;
7. `sudo -u deploy deploy/build.sh` — сайт с подсказками адреса и расчётом.

«Пояснение под выбором» в «Оплате» по умолчанию теперь: «Онлайн
оплачиваются блюда и доставка. Если адрес не найден на карте, стоимость
доставки назовём при звонке.» Если на проде это поле заполнено старым
текстом — очистить его.

**Адрес по пунктам — выкатка** (23.10.2026): `git pull`; `schema apply`
(четыре поля `orders.address_*`, адрес в несколько строк, подпись и условие
старого поля, порядок полей); сброс кеша схемы; `pnpm setup` — новые поля в
публичном и гостевом создании заказа и в чтении гостя (поля и порядок он
заводит и сам, если `schema apply` пропущен); `docker compose restart
directus`; сборка сайта с новой формой. Пустые пункты `order-guard` в запись
не передаёт, поэтому старая страница работает и до `pnpm setup`, а заказ с
пунктами до него получает 403 по правам на `address_flat`.

  выпадает, вопрос про приложение скрывается, сборка пишет об этом в журнал.

**Заявки.** Форма внизу каждой страницы: имя, телефон (маска `+7`), дата,
гостей, формат (кнопки или «Ещё не решили»), где (зал на Садовой, зал на
Советской Армии, выезд с адресом, «пока не знаю»), пожелания, согласие.
Обязательны только имя, телефон и согласие. Черновик формы хранится в
браузере, «Обсудить формат» на развороте выбирает формат в форме. После
отправки — экран «Заявка принята» с номером и тем, что гость указал; при
ошибке сети, 400 или 429 — понятное сообщение и номер для звонка. Без
`PUBLIC_DIRECTUS_URL` форма заменяется звонком.

В админке «Заявки на кейтеринг» открываются новыми сверху, закладки «Новые»
и «В работе» (в работе + договор). Пока статус «Новая», в карточке подсказка
перезвонить. Каждая заявка с сайта приходит уведомлением (колокольчик) ролям
«Administrator» и «Редактор»: «Заявка на кейтеринг 1210-4821 · 40 гостей»,
в тексте имя, телефон, дата, гости, формат, зал или адрес, пожелания.

**Защита заявки** — расширение `directus/extensions/request-guard`, как у
заказов: публичная роль только *создаёт* заявку и не читает ни одной; хук до
записи проверяет имя, российский телефон, согласие, дату (не в прошлом и не
дальше двух лет), гостей (1-2000), зал (существующий) или адрес, формат
(опубликованный); номер `ДДММ-NNNN`, статус «Новая» и источник «Сайт» ставит
сам, заметку менеджера от гостя не принимает. Не больше 5 заявок за 10 минут
с одного адреса (тот же `X-Forwarded-For` + `IP_TRUST_PROXY=1`). Заявка,
заведённая редактором в админке, хуком не проверяется. Правила хука и сайта
(`src/lib/request.ts`) одни и те же — паритет проверяет `pnpm test`. CORS —
тот же `CORS_ORIGIN`, что у заказов.

**Импорт со старого сайта.** REST API WordPress отдаёт у страниц пустой
`content` (тема рисует их PHP-шаблонами), поэтому `scripts/import-catering.mjs`
читает HTML пяти страниц (`/`, `/services/`, `/about/`, `/contacts/`, `/faq/`):
первый экран, цифры, приоритеты, форматы, шаги и переписку, постскриптум,
бонус заявки, все вопросы по темам и фото. Тексты переносятся как есть, с
лёгкой правкой (опечатки, «₽ на гостя» вместо «руб./чел.», неразрывные
пробелы); цены и «что входит» форматов собраны из ответов FAQ старого сайта
(источник — в комментариях `FORMAT_FACTS`). Фото — через `/files/import` в
папку «Кейтеринг» с осмысленными заголовком и alt. Связка записи с импортом —
поле `import_key`, файла — пометка в описании.

```bash
DIRECTUS_URL=http://127.0.0.1:8055 DIRECTUS_ADMIN_TOKEN=<токен админа> \
  node scripts/import-catering.mjs --dry-run   # что будет записано, без записи
node scripts/import-catering.mjs               # первый импорт: заводит недостающее, пустые поля страницы заполняет
node scripts/import-catering.mjs --sync        # переписать поля из импорта у уже заведённого (правки редактора будут потеряны)
```

Флаги: `--no-photos`, `--save file.json` (сохранить разбор), `--from file.json`
(импорт из сохранённого разбора без чтения страниц; фото всё равно берутся
со старого сайта), `--plan file.json` (что будет записано — для проверки
глазами), `OLD_SITE` — другой адрес старого сайта. Повторный запуск ничего не
дублирует и без `--sync` ничего не перезаписывает. Импорт нужно прогнать
**до** выключения старого сайта; без него раздел можно поднять из фикстуры
(`scripts/import-fixture.mjs` заливает и кейтеринг, если он пуст).

**Выкатка кейтеринга на прод** — строго по порядку:

1. `git pull` на сервере, `docker compose restart directus` — подхватить
   `request-guard` (в логе `Loaded extensions: …, directus-extension-request-guard`);
2. `schema apply` из шага 3 (`directus/snapshot.yaml`);
3. сброс кеша схемы (`/utils/cache/clear?system` или `restart directus`);
4. `pnpm setup` — права редактора на страницу, форматы, шаги, вопросы и
   заявки, сборщику — чтение раздела (не заявок), публичное «только создание»
   заявки, список и закладки заявок, Flow на коллекции раздела;
5. `node scripts/import-catering.mjs --dry-run`, затем без флага — с
   `DIRECTUS_URL` и токеном админа сервера;
6. `sudo -u deploy deploy/build.sh` и проверка: `/catering/`,
   `/catering/services/`, `/catering/faq/`, тестовая заявка, уведомление в
   админке, удалить тестовую заявку;
7. владельцу — переадресация старого домена: `vkusnayakompania.ru/` →
   `https://vkus-com.ru/catering/`, `/services/` → `/catering/services/`,
   `/faq/` → `/catering/faq/`, `/about/` → `/catering/#about`,
   `/contacts/` → `/catering/#contacts` (301).

## Личный кабинет и «Вкусные баллы»

С 19.10.2026 у гостя есть кабинет `/account/` (кружок с человеком в шапке,
оливковая точка — гость вошёл). Вход — по номеру телефона и коду, пароля нет.
В кабинете: баланс баллов и когда сгорают ближайшие, уровень и сколько осталось
до следующего, траты за месяц и всего, «Ваши акции» (с подарком и акциями ко
дню рождения), вкладки «Заказы» (статус, состав, суммы, «Повторить» — заказ
возвращается в корзину по текущим ценам), «Баллы» (каждая операция и правила
программы) и «Профиль» (ФИО, дата рождения, пол, почта для восстановления;
телефон только для чтения). Страница закрыта от индексации и не входит в
карту сайта.

В корзине при оформлении: не вошёл — «Войти по номеру» (вход шагом корзины,
потом обратно к заказу), с подсказкой, сколько баллов придёт за этот заказ;
вошёл — имя и телефон подставлены, ползунок и поле «Списать баллы», в подвале
«Баллами −… ₽» и «К оплате», после отправки — что списано и сколько начислим.

**Правила баллов** (1 балл = 1 ₽, все числа — в «Программе лояльности»):

| Что | Когда и сколько |
|---|---|
| За первый вход | `signup_bonus` (200) сразу, один раз на номер |
| За заказ с сайта | процент уровня от суммы, оплаченной деньгами (`to_pay`), — когда заказ переведён в «Выполнен». Уровень — по покупкам *до* этого заказа |
| Списание | при оформлении, не больше баланса и не больше `max_share_percent` (30 %) заказа после скидки именинника. Книга гостя пишется под `pg_advisory_xact_lock` по гостю: два заказа из двух вкладок встают в очередь, второй берёт остаток баллов, разница возвращается в «К оплате», причина — в заметке менеджера; два одновременных «Выполнен» дают одно начисление |
| Отмена | «Отменён» возвращает списанные баллы и снимает начисленные; вернули в «Выполнен» — снова списано и начислено. Ничего не дублируется |
| Сгорание | через `points_ttl_days` (365) после начисления; первыми тратятся и сгорают самые старые (FIFO). 0 — не сгорают |
| День рождения | `birthday_bonus` (500) раз в год, в окне ±`birthday_window_days` (3), если дату указали до начала окна; действуют до конца окна |
| Скидка именинника | `birthday_discount_percent` (0 — выключена): один заказ с сайта в окне дня рождения |
| Вручную | редактор заводит запись в «Операциях по баллам»: плюс или минус и комментарий, за что; тип всегда «Вручную», минус больше баланса не пройдёт |

Уровни — редактируемый список «Уровни»: название, «от … ₽ покупок», процент
(по умолчанию уровень 1: 0 ₽ — 3 %, уровень 2: 10 000 ₽ — 5 %, уровень 3:
30 000 ₽ — 7 %). «Программа включена» = выкл: сайт не показывает баллы, новые
не начисляются и не списываются, сгорание на паузе, возвраты по отменам идут.

**Коллекции** (группа «Личный кабинет»):

| Коллекция | Что | Кто правит |
|---|---|---|

| `guest_auth_settings` «Вход по телефону» (одна запись) | вход открыт, канал (звонок / SMS / мобильная авторизация), «Предлагать SMS», имя отправителя, текст SMS (`{code}`), подсказки (`{phone}`) | редактор |
| `bonus_transactions` «Операции по баллам» | гость, тип (регистрация, день рождения, начисление, списание, сгорание, откат, вручную), сумма ±, заказ, срок, комментарий; закладки «Вручную», «Сгорание» | редактор: чтение и только ручные записи; гость: чтение своих |

**Сколько брать с гостя.** В заказе из кабинета «Сумма» — по ценам блюд, а
брать нужно «К оплате» (сумма минус баллы и скидка). То же написано в
«Заметке менеджера»: «Личный кабинет — оплачено баллами: 200 ₽. К оплате
2 120 ₽». Онлайн-оплата (`pay`) просит у банка именно «К оплате», экран
«Заказ оплачен» показывает строку «Баллами и скидкой −200 ₽», а письмо и
Telegram менеджерам (`notify`) — «Итого: 2 320 ₽ · баллами −200 ₽ · к оплате
2 120 ₽». Чек 54-ФЗ при оплате баллами уходит без позиций: сумма позиций не
сходится с суммой платежа, и `pay` в этом случае отправляет чек без корзины
(раскладка скидки по позициям — следующий шаг). Заказ, принятый по телефону,
можно привязать к гостю полем «Гость (личный кабинет)» — баллы начислятся при
«Выполнен».

**Вход по телефону** — расширение `directus/extensions/guest-auth`:

- `POST /guest-auth/send` — код из 4 цифр живёт 5 минут, 5 попыток ввода;
  повторно — через минуту, не больше 5 кодов в час и 10 в сутки на номер,
  12 в час с адреса, 30 проверок за 10 минут с адреса.
- Канал из «Входа по телефону». **Звонок** (по умолчанию): код — последние
  4 цифры номера. На 19.10.2026 SMS Aero отвечает на звонок «Method not found»
  — услуга не подключена в аккаунте, поэтому каждый вход сейчас уходит SMS
  автоматически (если «Предлагать SMS» включено). **SMS**: текст из админки,
  отправитель «SMS Aero» (бесплатный) или своё имя после регистрации в SMS
  Aero. **Мобильная авторизация**: оператор просит гостя подтвердить вход на
  телефоне, иначе шлёт SMS с кодом; код проверяет SMS Aero, подтверждение
  страница опрашивает раз в 3 секунды.
- `POST /guest-auth/verify` `{ phone, code?, request }` — `request` это id,
  который выдал `/send`: с чужим или устаревшим id ответ «Код устарел», а
  подтверждение на телефоне (мобильная авторизация без кода) открывает сессию
  только браузеру, который начал вход. Код тратится одним запросом (условное
  `sent → used`): две одновременные проверки верного кода дают одну сессию;
  неверные попытки считаются в базе (`attempts + 1`), не по снимку запроса.
  Находит гостя по телефону или заводит нового
  (роль «Гость», служебная почта `<цифры>@guest.vkus-com.ru`, пароля нет,
  входа в админку нет) и выдаёт **токен сессии Directus на 30 дней**: JWT,
  подписанный `SECRET`, с записью в `directus_sessions`. Поэтому обычный REST
  работает от имени гостя под правами роли, а выход (`POST /guest-auth/logout`)
  и блокировка гостя (статус «Suspended») отзывают его сразу. Телефон
  сотрудника гостевой вход не открывает. Браузер хранит токен в
  `localStorage` и забывает его при выходе.
- `GET /guest-auth/me` — профиль, заказы, операции, правила программы;
  `POST /guest-auth/profile` — сохранить профиль (дату рождения гость
  указывает один раз, исправить может редактор).

**Режим отладки** — только для локального стенда: `GUEST_AUTH_DEBUG=true`
ничего не отправляет и пишет код в лог Directus (`docker compose logs
directus | grep guest-auth`), с `GUEST_AUTH_DEBUG_CODE=2468` подходит один
постоянный код. В логе при запуске — предупреждение «РЕЖИМ ОТЛАДКИ». Тестовый
ключ SMS Aero отправку SMS не разрешает («test not allowed»), работает только
мобильная авторизация (код 1234) — для проверки шлюза без денег.

**Хук `directus/extensions/loyalty`** ведёт книгу баллов: проверяет списание
при оформлении (`order-guard` спрашивает его до записи заказа), сверяет заказ
с операциями при каждом изменении статуса, дарит баллы за вход, ночью в
01:05 по Самаре (и через 20 секунд после запуска Directus — догнать
пропущенную ночь) сжигает просроченное и дарит баллы ко дню рождения,
пересчитывает баланс, уровень и сумму покупок гостя. Правила в
`directus/extensions/loyalty/rules.js` и `src/lib/loyalty.ts` одни и те же —
`pnpm test` гоняет одни случаи через оба файла.

**Переменные** (`directus/.env`, пробрасывает `docker-compose.yml`):

```env
SMSAERO_EMAIL=почта аккаунта SMS Aero
SMSAERO_API_KEY=боевой API-ключ (smsaero.ru → «Настройки» → «API»)

GUEST_AUTH_DEBUG_CODE=     # на боевом пусто
```

Сайту новых переменных не нужно: кабинет ходит на тот же `PUBLIC_DIRECTUS_URL`,

в шапке нет, а `/account/` предлагает позвонить.

**Сколько стоит вход** (SMS Aero, 19.10.2026, без НДС, уточнить в кабинете):
SMS с бесплатным отправителем — МТС 9,89 ₽ (цену вернула тестовая отправка
`sms/testsend`, деньги не списываются), МегаФон 14,19 ₽, Билайн 46,29 ₽,
Tele2 9,79 ₽ (прайс SMS Aero); звонок (Flash Call) в аккаунте не подключён —
подключение и цена у менеджера SMS Aero; мобильная авторизация — по тарифу
SMS Aero. Гость входит один раз на 30 дней, поэтому 300 входов в месяц —
примерно 3-6 тысяч ₽ при SMS.

**Смена номера и восстановление.** Почта для восстановления хранится в
профиле, но письма не уходят: SMTP не настроен. Пока так: гость звонит,
сотрудник открывает его карточку («Пользователи» → «Гость») и меняет
«Телефон (вход на сайт)» — баллы и заказы остаются. Когда появится SMTP,
по этой почте можно будет подтверждать смену номера.

**Выкатка кабинета на прод** — строго по порядку:

1. в `/srv/vkus/site/directus/.env` — `SMSAERO_EMAIL`, `SMSAERO_API_KEY`,
   `GUEST_AUTH_DEBUG=false`;
2. `git pull` на сервере;
3. `schema apply` из шага 3 (`directus/snapshot.yaml`) — коллекции кабинета,
   поля гостя, заказа и акций;
4. сброс кеша схемы (`/utils/cache/clear?system` или `restart directus`);
5. `pnpm setup` — роль и политика «Гость», права редактора и сборщика,
   закладки, Flow на «Программу лояльности» (внутри — `scripts/setup/account.mjs`);
   если `schema apply` пропущен — `node scripts/setup/account-schema.mjs`
   заводит то же самое и повторный запуск ничего не дублирует;
6. `docker compose up -d directus` (не `restart`: нужно перечитать env) — в
   логе `Loaded extensions: …, directus-extension-guest-auth,
   directus-extension-loyalty` и строка `loyalty: ночной проход …`;
7. `sudo -u deploy deploy/build.sh` и проверка: `/account/`, вход своим
   номером (придёт SMS), профиль, тестовый заказ с баллами, «Выполнен» в
   админке → начисление в кабинете; удалить тестовый заказ и операции,
   гостя оставить или удалить.

## Документы: оферта, политика, доставка, реквизиты

С 20.10.2026 условия магазина — открытые страницы сайта, а не файлы: их
требуют платёжные сервисы (ЮKassa, банк) до подключения онлайн-оплаты, и
гость читает их без входа.

| Адрес | Документ |
|---|---|
| `/docs/` | все документы списком: название, о чём, дата редакции |
| `/docs/offer/` | «Публичная оферта» — договор купли-продажи и доставки: доставка по зонам оплачивается вместе с заказом (п. 5.2), оплата на сайте только онлайн (п. 5.3), минимальный заказ по зоне (п. 6.3) |
| `/docs/delivery/` | «Доставка и оплата» — как заказать; шесть зон доставки со стоимостью, порогом бесплатной доставки и минимальным заказом, часы; самовывоз; оплата онлайн картой и баллами; электронный чек; отмена и возврат |
| `/docs/privacy/` | «Политика конфиденциальности» — 152-ФЗ |
| `/docs/requisites/` | «Реквизиты и контакты» — ИП, ИНН, ОГРНИП, связь, точки |

**Коллекция** `pages` «Документы»: заголовок, адрес страницы (`slug`,
латиницей, уникальный), «Кратко, для поиска» (description, до 160 знаков),
«Редакция от» (дата, сайт печатает «Редакция от 20 октября 2026»), текст
(WYSIWYG), статус, порядок (перетаскиванием — это и порядок в подвале). Новая
запись — черновик с плашкой. Удалять документы редактор не может: снятый
документ уходит в архив, адрес и история правок остаются. На сайт попадает
только «Опубликовано»; адрес черновика или архивного документа отвечает 404.

**Текст.** «Заголовок 2» — разделы: из них оглавление (с четырёх разделов —
сбоку на десктопе, свёрнутое над текстом на телефоне) и якоря
(`/docs/offer/#5-tsena-i-oplata`). «5. Цена и оплата» — номер раздела
выделяется терракотой, «5.3.» в начале абзаца — номер пункта уходит на поле.
Картинок в документах нет (в панели нет кнопки), скрипты, фреймы и
обработчики событий из вставки Word вычищаются на сборке. Короткие слова и
`№` не висят в конце строки, адрес сайта не рвётся на дефисе.

**Вставки** — данные из админки, которые обновляются сами:

| Вставка | Что на странице | Откуда |
|---|---|---|
| `[[реквизиты]]` | наименование, ИНН, ОГРНИП, адрес (если заполнен), сайт и кнопка «Скопировать реквизиты» | «Настройки» → юрлицо |
| `[[связь]]` | телефон, почта, Telegram, Max, ВКонтакте | «Настройки» → контакты |
| `[[точки]]` | обе точки: адрес, тип, телефон, часы по дням | «Точки» |
| `[[телефон]]` | общий номер ссылкой, внутри фразы | «Настройки» |

Первые три ставятся отдельным абзацем; внутри фразы такая вставка не
рисуется, а сборка пишет об этом строку в журнал (как и про опечатку в
скобках). Почта для гостей — новое поле «Настройки → Почта для обращений»
(`settings.email`): пустое — в «Связаться с нами» только телефон и
мессенджеры. Политика конфиденциальности ссылается на эти контакты для
отзыва согласия, поэтому почту стоит заполнить.

**Где сайт ссылается на документы.** Подвал каждой страницы — группа
«Документы» рядом с «Разделами»; юрстрока с ИП, ИНН и ОГРНИП под линией
остаётся. Галочки согласия в корзине, во входе в кабинет и в заявке на

## Акции: как набирать, чтобы лист не развалился

Секция «Акции» — печатный лист: первая акция по порядку (`sort`) — оттиск с
крупной цифрой, остальные — нумерованный реестр. Форму держит страница, а не
редактор, но три правила набора делают её лучше:

- **Заголовок — до 45 знаков**, одна мысль: «Скидка 20 % на первый заказ».
  Число со знаком `%` в заголовке первой акции страница вынимает и печатает
  крупно (`20 %`), остаток заголовка идёт подписью под ним. Без процента на
  месте цифры встаёт сам заголовок.
- **Текст — одно условие, до 110 знаков.** На странице остаётся первое
  предложение, остальное режется; в реестре — не больше трёх строк.
- **Первая по `sort` — витрина.** Ставьте первой общую акцию с процентом:
  оттиск с цифрой на бумаге и есть то, за что цепляется глаз. Точка задаётся
  полем `place`; пустое поле печатается как «Обе точки».

Окна показа (`show_from` / `show_until`) работают как прежде: вне окна акция
не собирается, ночной крон пересобирает сайт в 00:10.

Поле «Кому»: «Всем» (по умолчанию) — акция в секции «Акции»; «Именинникам» —
акция не печатается на главной, а показывается в личном кабинете гостю, у
которого сейчас окно дня рождения (см. «Личный кабинет и «Вкусные баллы»»).

**Приложения на сайте нет** (решение владельца 12.10.2026). Акция, в
заголовке или тексте которой есть «приложение», App Store, Google Play или
`vkusdostavka.shop`, на сайт не попадает, а сборка пишет в журнал
«акция «…» действует в приложении — на сайте не показана». Если скидка
действует и для заказов с сайта — уберите упоминание приложения из текста, и
акция вернётся. Так же из текстов главной («Настройки» → тексты секций)
выпадает каждое предложение про приложение. Поля приложения и старого
магазина (`app_ios`, `app_android`, `shop_url`, `shop_*`, а также
`delivery_title`, `delivery_text`, `delivery_note`, `app_screenshot`) в
схеме остались, но страница их не выводит — заполнять не нужно.

Поля `yandex_score`, `yandex_ratings`, `yandex_reviews`, `yandex_highlights`
в «Настройках» страница больше не показывает: цифры спорили с живым виджетом
Яндекс Карт, а источник у отзывов один — виджет. Заполнять их не нужно;
`yandex_award` («Хорошее место 2026») по-прежнему печатается.

## Локальная разработка

```bash
cd directus && cp .env.example .env    # заполнить SECRET, DB_PASSWORD, ADMIN_*
docker compose up -d
cd .. && cp .env.example .env          # DIRECTUS_URL=http://localhost:8055
pnpm setup                             # нужен DIRECTUS_ADMIN_TOKEN, см. выше
node scripts/import-catalog.mjs        # каталог доставки из магазина (тот же токен)
pnpm fixture                           # выгрузить контент в фикстуру
pnpm dev                               # http://127.0.0.1:4321
```

Заказы из корзины локально: в `directus/.env` —
`CORS_ORIGIN=http://127.0.0.1:4321,http://localhost:4321`, в `.env` сайта —
`PUBLIC_DIRECTUS_URL=http://127.0.0.1:8055`, затем `docker compose up -d directus`.
Вход в кабинет локально без SMS: в `directus/.env` — `GUEST_AUTH_DEBUG=true`
и `GUEST_AUTH_DEBUG_CODE=2468`, `docker compose up -d directus`; код любого
номера — 2468 (и он же в логе Directus).

Без `DIRECTUS_URL` в `.env` сайт собирается из `src/data/fixture.json`; файлы
фикстуры в `src/data/fixture-files/` лежат в git, поэтому сборка проходит на
чистом клоне и на CI без Directus. `pnpm fixture` их перезаписывает — после
правок контента в админке изменения в этой папке коммитятся вместе с
`fixture.json`. `public/media/` из них собирает `prebuild`, она в `.gitignore`.
